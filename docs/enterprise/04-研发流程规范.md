# 智学学堂 · 研发流程规范

> 配套 `03-研发组织与岗位说明书.md`。本文是**全体研发的日常行为准则**，新成员入职首日必读。
> 编制日期：2026-09-02
> **适用前提**：本规范取代现状中的「个人开发 + 人工验证」模式。在团队规模 < 3 人时，可暂缓第 5、9、10 章；但第 11 章「项目特有红线」**从第一天起必须无条件遵守**。

---

## 一、总览：一次需求从提出到上线的完整链路

```
需求提出（产品/运营/教研）
   ↓ 需求评审（准入：有背景、有目标、有验收标准、有指标）
开发就绪（DoR：设计评审通过、接口契约确定、用例评审通过）
   ↓ 分支开发 → 自测 → 提交 PR
代码评审（≥1 人 Approve，关键域 ≥2 人）
   ↓ CI 全绿（lint / 类型 / 单测 / 集成 / 构建）
合并到主干 → 自动部署预发环境
   ↓ QA 回归 + 产品验收
生产发布（灰度 → 全量）→ 线上验证 → 监控观察
   ↓ 数据回收 → 复盘
```

## 二、分支模型

### 2.1 采用 Trunk-Based（主干开发，短分支）

理由：团队规模在 30 人以下、需要高频发布时，长期分支的合并地狱成本远高于收益。

| 分支 | 生命周期 | 说明 |
|---|---|---|
| `main` | 永久 | **始终可发布**。任何时刻都可从 main 出包 |
| `feat/xxx` | ≤ 3 天 | 功能开发，从 main 切出，完成后 PR 合并 |
| `fix/xxx` | ≤ 1 天 | 缺陷修复 |
| `refactor/xxx` | ≤ 5 天 | 重构（需提前说明范围与验证方式） |
| `release/x.y` | ≤ 2 周 | 大版本发布时的临时稳定分支（仅在需要并行多版本时使用） |
| `hotfix/xxx` | ≤ 4 小时 | 线上紧急修复，从 main 切出，优先合并 |

### 2.2 规则

1. **分支存活越短越好**。超过 5 天的分支必须在周会说明原因。
2. **每天至少同步一次 main**（`git rebase origin/main` 或 merge），避免大偏差。
3. **禁止直接 push main**，一切经过 PR。
4. **功能开关**：未完成的大功能用开关控制，允许提前合并到 main，避免长期分支。
5. **一个 PR 只做一件事**：重构与功能不要混在一个 PR 里（历史上曾有「提交里只有 rename、修复从未进提交」的教训）。

## 三、提交规范

### 3.1 格式（沿用项目现有中文提交习惯 + Conventional Commits）

```
<type>(<scope>): <中文简述>

<正文：改了什么 + 为什么（不是怎么改）>

<脚注：关联任务号 / 破坏性变更说明>
```

**type 取值**

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（不改变外部行为） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `docs` | 文档 |
| `chore` | 构建/依赖/工具 |
| `migration` | **数据库迁移**（本项目特殊类型，需强制评审） |

**scope 用域代号**：`identity` `content` `assessment` `engine` `engagement` `family` `commerce` `platform` `web` `admin` `infra`

**示例**

```
fix(engine): 掌握度计算忽略时间衰减导致长期未练知识点仍显示已掌握

mastery_records 更新时未套用遗忘衰减因子，学生三个月未练习的
知识点仍保持高分，导致学习路径不再安排复习。

- 在 MasteryService.update 加入时间衰减（半衰期 14 天，可配置）
- 补充回归用例：模拟 90 天未练习场景

关联：TASK-1203
```

### 3.2 提交纪律

- **一次提交一个逻辑变更**，不要把「改 bug + 调格式 + 加注释」混在一起。
- **禁止提交临时文件**：`tools/_*.py`、`*.log`、`temp/`、`data/`、`output/`、`.env`（已在 `.gitignore`，但需保持警惕）。
- **禁止提交密钥**：密钥一律走环境变量/密钥管理。提交前用扫描工具检查。
- **提交信息用中文**（与项目历史一致），但代码标识符、注释中的技术术语保持英文。

## 四、代码评审（Code Review）

### 4.1 门槛

| 变更类型 | 要求 |
|---|---|
| 普通功能/修复 | ≥ 1 人 Approve |
| 关键域（engine / commerce / identity） | ≥ 2 人 Approve，其中 1 人为域 Owner 或技术负责人 |
| 数据库迁移 | 域 Owner + 技术负责人 Approve |
| 支付/资金相关 | **双人评审 + 安全合规知会** |
| 涉及未成年人个人信息 | **安全合规 Approve** |
| 紧急 hotfix | ≥ 1 人 Approve（可事后补评审，但 24 小时内必须完成） |

### 4.2 评审 SLA

- 首次响应：**4 个工作小时内**（不是"有空再看"）。
- 评审完成：**24 小时内**。
- 超时未响应，作者有权在群里 @ 提醒或找 Backup。

### 4.3 评审清单（Reviewer 必须逐项确认）

**功能与正确性**
- [ ] 逻辑正确，边界条件已处理（空值、超限、并发、重复提交）
- [ ] 异常路径有处理与日志
- [ ] 幂等性（尤其写操作与支付相关）

**架构与规范**
- [ ] 未跨越域边界（无跨域直接 import 模型/直接 JOIN 其他域的表）
- [ ] 遵循既有分层（router → service → repository）
- [ ] 无重复实现（先查是否已有工具函数）

**项目特有红线**（见第 11 章）
- [ ] **未持有 DB 会话发起外部调用**（AI/HTTP/邮件/短信）
- [ ] 前端改动已确认会重建 dist
- [ ] 迁移脚本幂等且可回滚

**质量**
- [ ] 有对应测试，且测试有意义（不是为覆盖率而写的空断言）
- [ ] 命名清晰，无魔法数字
- [ ] 复杂逻辑有注释说明「为什么」
- [ ] 无调试代码、无用注释、被注释掉的代码块

**安全与合规**
- [ ] 无硬编码密钥
- [ ] 用户输入有校验（防注入、越权）
- [ ] 涉及个人信息的最小必要，且已有合法处理依据
- [ ] 日志中无敏感信息（手机号、身份证、Token、密码）

### 4.4 评审文化

- **对事不对人**：评论针对代码，不针对作者。
- **区分阻塞与非阻塞**：用 `[阻塞]` / `[建议]` / `[疑问]` 前缀标注，避免无限拉锯。
- **作者有权解释**：如果 reviewer 误解，作者应补充说明而非直接照改。
- **评审不是走过场**：发现「看不懂但先 Approve」的情况，视为评审失职。

## 五、测试策略与质量门禁

### 5.1 测试金字塔

| 层级 | 占比目标 | 工具 | 说明 |
|---|---:|---|---|
| 单元测试 | 60% | pytest | 服务层纯逻辑，快速、无外部依赖 |
| 集成测试 | 30% | pytest + TestClient + MySQL `_test` 库 | 接口 + 数据库，现有 124 用例属此层 |
| 契约测试 | 5% | 自定义 / schemathesis | 跨域接口，防止接口漂移 |
| E2E 测试 | 5% | Playwright | 关键链路（注册→答题→判分→支付） |

### 5.2 覆盖率门禁（CI 强制）

| 范围 | 要求 |
|---|---|
| 全局 | ≥ 70%（逐步提升，不一步到位） |
| D4 学习引擎 | ≥ 85% |
| D7 交易商业化 | ≥ 90% |
| D1 身份与权限 | ≥ 80% |
| D9（IM/账本，冻结域） | 豁免，但**禁止新增未测试代码** |

### 5.3 测试纪律

- **测试必须可重复**：禁止依赖外部网络、真实 AI 调用、真实支付（全部打桩）。现有 `conftest.py` 已打桩 AI/邮件，需保持。
- **禁止 flaky 测试**：不稳定的测试立即修复或标记跳过并登记，不允许「重跑一次就好」。
- **回归套件时长受控**：超过 15 分钟需分层并行（当前 124 用例约数分钟，新增时需注意）。
- **bug 修复必须带回归用例**：修完不补测试，等于没修。
- **测试数据隔离**：沿用 `DB_NAME + "_test"` 独立库，禁止测试连接生产库（现有 conftest 已有安全护栏，需保持）。

### 5.4 现有盲区（需在本期补齐）

| 域 | 端点 | 现状 | 要求 |
|---|---:|---|---|
| D9 IM | 29 | **0 覆盖** | 冻结后豁免；若保留必须补 |
| D9 账本 | 42 | **0 覆盖** | 同上 |
| D7 交易 | 待建 | — | 建即覆盖 ≥ 90% |
| D4 学习引擎 | 待建 | — | 建即覆盖 ≥ 85% |

## 六、CI/CD 流水线

### 6.1 现状与差距

**现状：无 CI**。测试靠人工执行，构建靠本地 `npm run build`，部署靠服务器 `git pull && bash deploy.sh`。

### 6.2 流水线设计

**PR 阶段（每次提交触发）**

```
1. 代码检出 + 依赖缓存
2. Lint（ruff / flake8）+ 格式化检查（black --check）
3. 类型检查（mypy，渐进启用）
4. 单元测试（pytest -m unit）
5. 架构约束检查（禁止跨域 import —— import-linter）
6. 密钥扫描（gitleaks / detect-secrets）
7. 依赖漏洞扫描（pip-audit / safety）
8. 构建检查（前端 npm run build 能通过）
```

**合并到 main 后**

```
9. 集成测试（pytest，MySQL _test 库）
10. 契约测试
11. 构建产物（web/dist、admin/dist）
12. 部署预发环境
13. E2E 冒烟
```

**发布阶段（手动触发）**

```
14. 数据库迁移（预发验证 → 生产执行，需人工确认）
15. 生产灰度发布（先小流量/单实例）
16. 冒烟验证 + 监控观察 15 分钟
17. 全量发布
18. 线上验证 + 指标观察 24 小时
```

### 6.3 门禁规则

- **任一阶段失败，禁止合并**（PR 阶段）。
- **hotfix 可跳过非关键阶段**（如类型检查），但测试与安全扫描不可跳过。
- **流水线配置本身也需评审**（`.github/workflows/` 变更走 PR）。

## 七、发布与回滚

### 7.1 发布节奏

| 类型 | 频率 | 说明 |
|---|---|---|
| 常规发布 | 每周 1–2 次（固定窗口，如周二/周四 20:00 后） | 避开学习高峰（18:00–21:00 是孩子使用高峰） |
| 紧急修复 | 随时 | 走 hotfix 流程 |
| 大版本 | 按需 | 需发布说明与灰度计划 |

> **注意**：本项目已有夜间免打扰机制（22:30–07:00 拦截动作类端点），发布窗口也应避开学生活跃时段，建议在 **22:00 后或 07:00 前**，或明确告知用户的低峰期。

### 7.2 发布检查清单

- [ ] 全量测试通过
- [ ] 数据库迁移已在预发验证，且幂等、可回滚
- [ ] 前端 dist 已重建（**本项目高频坑**：改了前端不 build，线上仍是旧产物）
- [ ] 配置项与密钥已在生产环境就绪
- [ ] 监控告警已就位（新功能有对应指标）
- [ ] 回滚方案明确（代码回滚 + 数据回滚）
- [ ] 相关方已知会（运营/客服）

### 7.3 回滚原则

1. **代码回滚优先于修复前进**：线上出问题时，先回滚恢复服务，再排查。
2. **数据变更必须可回滚**：迁移脚本必须提供反向脚本，或明确声明不可回滚并由技术负责人批准。
3. **灰度发布**：新功能用开关控制，先对内部账号/小比例用户开放。
4. **回滚后必须复盘**：不允许「回滚了就没事了」。

### 7.4 数据库迁移纪律（本项目重点）

现有 `app/migrations/` 是自建 runner（56 个脚本，001–025 为 SQLite 历史基线，026+ 幂等执行）。需补充：

| 规则 | 说明 |
|---|---|
| `migration` 类型单列 | 迁移脚本单独一个 PR，不与业务代码混合 |
| 强制幂等 | 重复执行不报错、不产生副作用 |
| 强制回滚方案 | 附反向脚本或声明不可回滚的理由 |
| 大表变更评审 | 影响 > 100 万行的变更需技术负责人评审，明确执行窗口、锁表风险、回滚预案 |
| 禁止运行时 DDL | 迁移只在发布流程执行；现有的 `_ensure_column` 兜底逻辑逐步收敛移除 |
| 禁止直连克隆库写入 | 本地克隆库（`192.168.2.158`）仅用于同步与只读验证，**写线上内容必须走线上发布流程** |
| 题库版本脚本纳管 | 现有 `qb_versions/` 手工传线上执行的做法需纳入评审与版本管理，禁止无记录的线上数据变更 |

## 八、缺陷管理

### 8.1 分级与 SLA

| 级别 | 定义 | 响应 | 修复 | 示例 |
|---|---|---|---|---|
| **P0 致命** | 服务不可用、资金损失、数据泄露、合规事故 | 15 分钟 | 4 小时内恢复 | 全站 500、支付错乱、信息泄露 |
| **P1 严重** | 核心功能不可用，无绕过方案 | 1 小时 | 24 小时 | 无法答题、判分全错、掌握度计算错误 |
| **P2 一般** | 功能异常但有绕过方案，或影响部分用户 | 4 小时 | 3 个工作日 | 某题型判分偶发错误、页面样式错乱 |
| **P3 轻微** | 体验问题、文案错误 | 1 工作日 | 下个迭代 | 错别字、提示不友好 |

### 8.2 缺陷处理流程

1. **录入**：必须含环境、复现步骤、期望/实际、影响范围、截图或日志。
2. **定级**：由 QA + 产品经理共同定级。
3. **根因分析**：P0/P1 必须写明根因，不允许只描述现象。
4. **回归用例**：修复后补测试，防止复发。
5. **同类排查**：P0/P1 需排查是否存在同类问题（例如判分错误需排查全部题型）。

## 十、值班与应急响应

### 10.1 值班机制

- M2 起建立轮值（研发 + SRE），7×24 覆盖（可通过告警升级实现，非实时盯屏）。
- 值班人员职责：接收告警、初步判断、升级、协调、记录时间线。
- 值班交接有书面记录（未闭环事项）。

### 10.2 故障响应流程

```
告警触发 → 值班 5 分钟内确认 → 判断是否 P0
   ↓ P0
立即响应：止血优先（回滚/降级/限流）
   ↓
通知相关方（技术负责人、产品、运营/客服）
   ↓
排查根因 → 修复 → 验证 → 恢复
   ↓
48 小时内输出 RCA 报告
```

### 10.3 RCA 报告要素（无责复盘）

1. **时间线**：何时发生、何时发现、何时恢复（精确到分钟）
2. **影响范围**：影响用户数、时长、是否有资金/数据损失
3. **根因**：技术上为什么发生（5 Whys）
4. **为什么没被更早发现**：监控/测试/评审的缺口
5. **改进项**：具体行动、责任人、时限（**必须有闭环验证**）
6. **不做指责**：复盘对事不对人

> 本项目历史上曾发生「持 DB 连接调用外部 AI 导致连接池耗尽、全站卡死」的事故，其教训已固化为第 11 章红线，RCA 文档应保留供新人学习。

## 十一、项目特有红线（从第一天起无条件遵守）

> 这些是本项目用真实故障换来的教训，不遵守会直接导致线上事故。

| # | 红线 | 原因 | 检查方式 |
|:--:|---|---|---|
| 1 | **严禁持有 DB 会话发起外部阻塞调用**（AI/HTTP/邮件/短信） | 曾导致连接池耗尽、全站 TimeoutError 卡死 | Code Review 必查；正确模式：短会话读写 → 关闭 → 调外部 → 再开短会话写回 |
| 2 | **前端改动必须重建 dist** | 后端托管的是 `web/dist`/`admin/dist` 构建产物，不 build 则线上无变化 | 发布清单必查 |
| 3 | **MySQL 的 TEXT/MEDIUMTEXT 列不允许 DEFAULT** | MySQL 报 1101 错误；跨方言加列须用 `app/database.py` 的 `_ensure_column` | 迁移评审必查 |
| 4 | **迁移脚本必须幂等** | runner 按编号顺序执行，重复执行不能报错 | 迁移评审必查 |
| 5 | **禁止本地沙箱直连克隆库写入线上内容** | 克隆库（`192.168.2.158`）是线上库的本地复刻，写入会造成数据错乱 | 环境约定 + 发布流程约束 |
| 6 | **数据采集/批量任务排凌晨 01:00** | 用户约定：批量、定时、汇总类任务统一在低峰执行 | `tools/scheduler.py` 任务声明规范 |
| 7 | **大文本字段跨方言处理** | MySQL 需 MEDIUMTEXT，SQLite 需 TEXT；用 `models/paper.py` 的 `_longtext()` 编译钩子，不能靠 try-import 判断方言 | 模型评审必查 |
| 8 | **重构进行中禁止用 `git checkout -- <dir>` 恢复** | 会丢弃该目录全部未提交修改（曾有惨痛教训：拆分后的导入修复被整体回滚） | 团队约定 |

## 十二、文档规范

### 12.1 必须有的文档

| 文档类型 | 存放 | 时机 |
|---|---|---|
| 架构决策记录（ADR） | `docs/adr/NNN-标题.md` | 每个重大技术决策（选型、拆分、数据模型变更） |
| 域边界与职责 | `docs/data-ownership.md` + 各域 README | 建立时 + 变更时 |
| 接口文档 | 自动生成（FastAPI OpenAPI）+ 契约文件 | 接口变更时 |
| 指标字典 | 数据负责人维护 | 指标新增/变更时 |
| 运维手册（Runbook） | `docs/runbook/` | 每个告警规则配套 |
| 发布说明 | `docs/releases/` | 每次发布 |

### 12.2 ADR 模板

```markdown
# ADR-001：掌握度模型采用 BKT 还是自研加权模型

- 日期：2026-09-xx
- 状态：提议 / 已接受 / 已废弃 / 被取代
- 决策者：技术负责人、学习引擎后端、教研负责人

## 背景
（问题是什么，约束是什么）

## 备选方案
1. 方案 A：...
2. 方案 B：...

## 决策
选择方案 X，理由：...

## 后果
正面：...
负面：...（需要接受的代价）
需要跟进的事：...
```

### 12.3 文档纪律

- **没有文档的工作视为未完成**（架构决策、指标定义、接口变更）。
- **文档与代码同步更新**：改了代码不改文档，视为缺陷。
- **文档口径需可自检**：如 `PROJECT_STRUCTURE.md` 文末提供的口径自检命令，数字类文档必须提供刷新方式，避免再次漂移。

## 十三、Definition of Ready / Done

### 13.1 DoR（需求可以开始开发的准入条件）

- [ ] 有明确的背景与目标（解决谁的什么问题）
- [ ] 有可验证的验收标准
- [ ] 有衡量指标（如何判断做成了）
- [ ] 交互与视觉稿已确认（前端相关）
- [ ] 接口契约已评审（跨端/跨域相关）
- [ ] 合规审查已通过（涉及个人信息/未成年人/支付）
- [ ] 技术可行性已确认，方案已评审（复杂需求）

### 13.2 DoD（开发完成的判定标准）

- [ ] 功能符合验收标准，自测通过
- [ ] 单元测试 + 集成测试已补充，覆盖率达标
- [ ] CI 全绿
- [ ] Code Review 已 Approve
- [ ] 涉及文档（接口、指标、ADR）已更新
- [ ] 监控与告警已就位（新功能有指标）
- [ ] 无临时文件、无调试代码、无硬编码密钥
- [ ] 已在预发环境验证
- [ ] 回滚方案明确
- [ ] 迁移脚本（如有）已评审且幂等可回滚
- [ ] 遵守第 11 章全部红线

## 十五、规范落地建议（渐进实施）

不要一次性推行全部规范。建议顺序：

| 阶段 | 推行内容 | 理由 |
|---|---|---|
| 第 1 个月 | 第 11 章红线、提交规范、Code Review | 成本最低、收益最高，先止血 |
| 第 2 个月 | 分支模型、测试门禁、DoD/DoR | 建立协作基本盘 |
| 第 3 个月 | CI 流水线、缺陷分级、文档规范（ADR） | 自动化替代人工 |
| 第 4–6 个月 | 值班与应急、安全合规自动化检查、覆盖率门禁 | 规模化准备 |

> **规范的敌人是形式主义**。如果一条规范长期无人遵守，要么废掉它，要么改到可执行——不要让团队养成「规范只是写在文档里」的习惯。
