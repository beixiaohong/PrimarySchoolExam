## 一、为什么教育产品的产品团队不一样

互联网产品的产品团队通常是「产品经理 + 设计」。但教育产品多了一个决定性角色——**教研**。

原因很直接：
- 推荐错了商品，用户划走；**推荐错了题目，孩子的时间被浪费且家长信任崩塌**。
- 内容不是「数据」，是**有对错、有难度梯度、有教学顺序的专业资产**。
- 掌握度模型（本产品的核心）需要「知识点粒度」「掌握标准」「难度分级」这些**教育专业判断**，工程师无法自行定义。

因此本产品的产品团队是**三驾马车**：**产品（定义做什么） + 设计（定义长什么样） + 教研（定义什么是对的）**，运营与数据提供反馈闭环。

## 三、岗位说明书（产品与设计线）

### 3.1 产品负责人（CPO）

| 项 | 内容 |
|---|---|
| **定位** | 产品方向的最终决策者，对产品的商业成功负责 |
| **核心职责** | ① 制定产品战略与路线图（M0–M3）；② 确定优先级，裁定资源冲突；③ 定义北极星指标与成功标准；④ 把关产品定位与用户价值，抵制功能堆砌；⑤ 组建与培养产品团队；⑥ 对商业化结果（付费转化、留存、营收）负责 |
| **负责范围** | 全局；`docs/enterprise/01-产品优化方案.md` 的 Roadmap 维护 |
| **任职要求** | 5 年以上产品经验，2 年以上负责人经历；有教育/儿童产品或内容产品经验；能做减法——**在产品战略上，「不做什么」比「做什么」更重要**；有商业化实操经验 |
| **协作接口** | 向创始人汇报；与教研负责人共建内容战略；与技术负责人共建可行性；与运营负责人共建增长与变现 |
| **考核指标** | 北极星指标（周活跃用户掌握度提升量）；付费转化率与续费率；留存（次月留存）；关键路线图里程碑达成率 |

---

### 3.2 产品经理 · 学习线

| 项 | 内容 |
|---|---|
| **定位** | 学生端学习主线的产品 Owner，对「诊-学-练-测」闭环的效果负责 |
| **核心职责** | ① 学习主线功能设计：诊断测评、学习路径、练习、错题、复习、AI 讲题；② 与学习引擎后端 + 教研共同定义掌握度模型的产品语义（什么算"掌握"、如何呈现给孩子）；③ 学习效果的可视化设计（让孩子有掌控感、进步感）；④ 设计防止「刷量」的机制（引导真实掌握而非刷对题数）；⑤ A/B 实验设计与效果归因 |
| **负责模块** | 学生端：`web/src/views/` 中 Practice / Papers / Recite / Sync / Reading / Wrong / Stats / Knowledge / LearningGoals / Aiquiz / Assistant；后端域 D3（测评）+ D4（学习引擎） |
| **任职要求** | 3 年以上产品经验；有教育/学习类产品经验优先；**理解学习科学基础**（遗忘曲线、最近发展区、刻意练习）；能与算法工程师对话（理解模型能力边界）；数据驱动，会设计实验 |
| **产出标准** | PRD 含背景、目标、验收标准、成功指标；每个功能上线后有数据回收报告；效果类功能必须设计对照实验 |
| **考核指标** | 路径完成率；掌握度提升速率；人均有效练习时长；讲解后正确率提升 |

### 3.3 产品经理 · 家长线

| 项 | 内容 |
|---|---|
| **定位** | 家长价值的实现者——**家长是付费决策者** |
| **核心职责** | ① 家长端（含学生端内的家长入口）产品设计：学情中心、掌握度报告、周月报、干预建议、任务设置、管控；② 把数据转化为**可执行的建议**（而非数据罗列）；③ 家长信任建设：效果可信、隐私可控、沟通有温度；④ 家长端与孩子端的边界设计（监督但不监控，避免亲子冲突）；⑤ 家长反馈收集与转化 |
| **负责模块** | 家长端（M1 新建）、`web/src/views/Settings`、`/api/parent` `/api/appeal` `/api/tasks`(设置部分)、`/api/learning-goals` |
| **任职要求** | 3 年以上产品经验；**有家长视角**（自己有孩子或深度接触过家长群体优先）；懂数据可视化表达；有同理心，能理解家长焦虑与孩子压力的冲突 |
| **产出标准** | 每份学情报告必须包含 ≥ 1 条可执行建议；家长功能上线后有打开率与满意度数据 |
| **考核指标** | 家长周报打开率 ≥ 40%；家长端活跃率；家长满意度/NPS；家长付费转化贡献 |

### 3.4 产品经理 · 商业化与增长（M2）

| 项 | 内容 |
|---|---|
| **定位** | 让产品可持续地获得用户与收入 |
| **核心职责** | ① 会员体系设计（VIP/SVIP 分层权益、定价、试用）；② 付费转化链路设计（免费→试用→付费→续费）；③ 增长机制（邀请裂变、分享、渠道归因、召回）；④ 付费墙位置与免费额度策略（**平衡变现与体验**）；⑤ 与运营配合策划活动；⑥ 商业化数据分析（转化率、ARPU、LTV、续费率、退款率） |
| **负责模块** | D7 交易域的前端与流程；活动与优惠券；定价页与支付流程 |
| **任职要求** | 3 年以上产品经验，有订阅制产品操盘经验；熟悉应用内付费与会员体系；懂增长方法论（漏斗、AARRR、K 因子）；**有底线——不做伤害未成年人的商业设计**（如诱导充值、制造焦虑） |
| **考核指标** | 付费转化率；ARPU；续费率；LTV/CAC；退款率（越低越好）；免费用户活跃度（不因付费墙崩塌） |

### 3.5 产品经理 · 平台与后台（M2）

| 项 | 内容 |
|---|---|
| **定位** | 内部效率的产品化，让运营/内容/客服能自助工作 |
| **核心职责** | ① 管理后台（`admin/`）功能规划：用户管理、内容管理、审核工作台、数据看板、活动配置；② 内部工具产品化（减少研发手工操作）；③ 权限与审计设计；④ 与运营共建工作流；⑤ 老师端/机构端（M2 试点） |
| **负责模块** | `admin/src/` 全部页面；D8 平台域的产品侧；M2 的老师端 |
| **任职要求** | 3 年以上 B 端/中后台产品经验；能与运营深度协作；理解权限模型与审计需求 |
| **考核指标** | 运营自助率（无需研发介入的操作占比）；后台操作效率（如内容上线耗时）；后台事故率（误操作） |

### 3.6 交互设计师（UX）

| 项 | 内容 |
|---|---|
| **定位** | 学习体验的架构师 |

| **产出标准** | 关键流程有原型与可用性测试结论；交互规范文档化；与前端共建组件库 |
| **考核指标** | 任务完成率（可用性测试）；关键流程操作步骤数；设计返工率 |

## 四、岗位说明书（教研与内容线）

### 4.1 教研负责人

| 项 | 内容 |
|---|---|
| **定位** | 教育专业性的最终把关人，对「教什么、什么算会、怎么教」负责 |
| **编制** | **M0: 1 人（第 4 优先招聘）** |
| **核心职责** | ① **构建并维护知识点体系**（小学 1–6 年级 + 初中 7–9 年级，数学/语文/英语三科）——这是掌握度模型与个性化推荐的燃料，**M0 关键路径**；② 定义掌握标准（什么程度算"掌握"、如何分级）；③ 定义题目难度分级与知识点标注规范；④ 制定内容质量标准与审核标准；⑤ 诊断测评的试卷设计与效度验证；⑥ 学习路径的教学顺序设计（知识点依赖关系）；⑦ 带领学科教研团队；⑧ 审核 AI 生成内容的教育专业性 |
| **负责范围** | `knowledge_points` 表的内容标准、`problem_types` 定义、教材版本适配、诊断测评设计；与 D2 内容域、D4 学习引擎域深度协作 |
| **任职要求** | 8 年以上教育行业经验（公立学校 + 教育机构背景优先）；有课程体系/知识点体系搭建经验（如参与过教材编写、课程标准制定）；**懂教育测量**（难度、区分度、信效度）；能与工程师对话（理解模型能做什么、不能做什么）；有团队管理经验 |
| **产出标准** | 知识点树有版本管理与变更说明；每个知识点有明确的前置依赖与掌握标准；诊断测评有信效度验证报告；AI 生成内容有抽检标准 |
| **协作接口** | 与学习引擎后端共建掌握度标定；与内容域后端共建标注规范；与产品经理把教育专业性翻译成产品语言；与内容运营共建质量闭环 |
| **考核指标** | 知识点覆盖率；题目标注准确率（抽检）；诊断测评信效度；内容争议率（越低越好） |

### 4.2 学科教研（语文 / 数学 / 英语 / 初中）

| 项 | 内容 |
|---|---|
| **定位** | 单学科内容质量与教学设计的责任人 |
| **编制** | M0: 1 人（兼多科）；M1: 2 人；M2: 4 人（语/数/英/初中各 1） |
| **核心职责** | ① 本学科知识点体系细化与维护；② 题目编写、改编与审核（含解析质量）；③ 答案标准制定（含多解、容错边界——历史上曾因浮点舍入、中文数字、`10/3` 近似等产生 8 次判分修复，需把这些经验沉淀为学科答案规范）；④ AI 生成题目的抽检与修订；⑤ 教学内容设计（讲解要点、易错点、典型错误）；⑥ 与教材版本同步（人教/北师大/苏教等） |
| **负责范围** | 本学科题目与讲解内容；`questions`、`knowledge_points` 的学科维度 |
| **任职要求** | 3 年以上学科教学经验（小学/初中一线教师背景优先）；熟悉本学段教材与课程标准；**严谨**——一道错题的破坏力远大于十个缺失功能；能与工程师沟通判分规则（如"3.14 与 π 都算对"这类边界） |
| **产出标准** | 题目入库前过「可解性 + 答案正确性 + 解析完整性」三关；参与抽检（≥ 5%）；争议题 24 小时内给出裁定 |
| **考核指标** | 内容抽检合格率 ≥ 98%；争议率；内容产出量；AI 生成内容修订率 |

| **考核指标** | 内容入库 throughput；抽检合格率；争议处理时长；知识点题目覆盖均衡度 |

## 五、协作机制

### 5.1 需求流转全流程

```
① 需求来源
   用户反馈 / 数据洞察 / 竞品对标 / 教研建议 / 合规要求 / 战略拆解
        ↓
② 需求池登记（统一模板：来源、描述、影响面、初步价值判断）
        ↓
③ 需求评审（产品 + 教研 + 设计 + 研发 + 数据，双周一次）
   裁定：做 / 不做 / 再观察 —— 输出优先级与理由
        ↓
④ 方案设计
   产品：PRD + 验收标准 + 成功指标
   教研：教育专业方案（知识点/难度/标准）
   设计：交互稿 + 视觉稿
   研发：技术方案 + 接口契约
        ↓
⑤ 方案评审（含合规审查：未成年人/个人信息/内容安全/支付）
        ↓
⑥ 开发（DoR 达成后启动）→ 见《04-研发流程规范》
        ↓
⑦ 验收（产品验收 + 教研内容验收 + QA 质量验收，三方独立）
        ↓
⑧ 发布 → 数据回收（指标是否达成）
        ↓
⑨ 复盘（做成了吗？学到什么？要不要迭代？）
```

### 5.2 三方验收机制（教育产品必需）

| 验收方 | 验什么 | 不通过则 |
|---|---|---|
| **产品** | 功能是否符合 PRD 与验收标准、体验是否达标 | 退回迭代 |
| **教研** | 内容是否正确、难度是否合适、讲解是否专业 | **阻断发布**（内容错误是信任事故） |
| **QA** | 质量门禁（测试覆盖率、缺陷、性能、安全） | 阻断发布 |

> 三者独立验收、任一不通过不得发布。**教研的一票否决权必须明确**——这是教育产品与一般互联网产品的关键区别。

## 六、关键协作场景规范

### 6.1 教研 × 学习引擎后端：掌握度模型标定

这是**最难也最重要**的跨职能协作，需明确机制：

| 环节 | 教研负责 | 后端负责 | 共同产出 |
|---|---|---|---|
| 知识点粒度 | 定义知识点的粗细（太粗无区分度，太细无题可用） | 评估数据量是否支撑该粒度 | 知识点树 v1 |
| 掌握标准 | 定义"什么算掌握"（如连续 3 次正确且用时正常） | 转化为可计算规则 | 掌握度判定规则 |
| 标定验证 | 人工标注一批学生的真实掌握情况 | 用模型计算同一批学生 | 一致性检验报告（相关性 ≥ 0.7 方可上线） |
| 迭代 | 根据争议案例调整标准 | 调整模型参数 | 版本化记录 |

**机制**：每两周一次标定会，争议案例逐条过。**模型不准时先怀疑标准定义，再怀疑算法**。

### 6.2 教研 × 测评后端：判分边界定义

历史上 8 次判分准确性修复（浮点舍入、中位数奇偶、中文数字容差、`10/3` 近似等）说明：**判分边界必须由教研定义，不能由工程师想当然**。

规范：
- 教研为每种题型输出《答案规范》，含：等价答案（如 0.5 = 1/2 = 50%）、容差（如 π 取 3.14）、必答要素、错误典型。
- 后端把每条规范写成可执行的校验规则，并配套回归用例。
- 新增题型必须同步产出《答案规范》，否则不予开发。

### 6.3 内容运营 × 教研 × 后端：内容质量闭环

```
用户申诉/举报 ──┐
AI 复核存疑 ─────┼──→ 争议池 ──→ 教研裁定 ──→ 修订/下线
抽检不合格 ─────┘                    │
                                     └──→ 反馈给采集/生成环节，修正源头
```

- 争议题 24 小时内给出教研裁定。
- 高频争议题自动进入复核队列（现已有 `judge_review_issues`、`content_reviews` 表，需打通为自动化流程）。
- 每月输出《内容质量报告》：争议分布、高频错题、知识点缺口。

## 八、给小规模团队的特别建议

当前项目由个人开发者 + AI 辅助推进，上述角色无法一步到位。务实路径：

### M0 阶段（1–3 人）的最小可行配置

| 角色 | 如何替代 |
|---|---|
| 产品负责人 | 创始人自身 |
| 产品经理 | 创始人自身（用 PRD 模板强制自己写清楚背景/目标/验收标准/指标，避免拍脑袋） |
| 教研 | **外聘兼职教研顾问**（退休教师、教育机构教研），按知识点体系项目付费；这是**最不能省的钱** |
| UX/UI | 外包或复用成熟组件库（Element Plus 已在用）；**交互原则：不做创新，先做不犯错** |
| 内容运营 | 创始人兼（采集管线的自动校验做好，人工只处理异常） |
| 用户研究 | 直接找 5–10 个真实家长用户建群，每周聊一次 |

### 三个不要

1. **不要在没有教研的情况下做掌握度模型**。没有专业标定，模型只是自娱自乐的数字。
2. **不要用「我觉得」代替用户验证**。找 10 个真实家长比自己想 100 个需求有用。
3. **不要把产品工作简化为「画原型」**。PRD 里最有价值的部分是「背景、目标、成功指标」，不是界面图。
