## 一、组织设计原则

### 1.1 原则

| 原则 | 说明 |
|---|---|
| **按域负责，不按层负责** | 一个工程师对某个业务域端到端负责（接口 + 服务 + 数据 + 前端对接），而不是「后端只写接口、前端只写页面」。减少交接损耗与责任真空 |
| **小队制（2 Pizza Team）** | 每个业务域一个 2–5 人小队，含后端 + 前端 + 测试；小队内可独立完成需求交付 |
| **平台组服务业务组** | 平台组提供基建（身份、配置、埋点、推送、CI/CD），业务组不重复造轮子 |
| **Owner 制** | 每个域有且仅有一个 Owner（第一责任人），Owner 可变更但必须明确；Owner 不在时指定 Backup |
| **先补关键岗，不急着铺开** | 团队规模应匹配阶段（见 1.2），过早扩张会拖垮管理带宽 |

### 1.2 分阶段人才配置

> 当前状态：个人开发者 + AI 辅助。以下配置按阶段递增，**不是一上来就要招满**。

| 阶段 | 团队规模 | 新增关键角色 | 说明 |
|---|---:|---|---|
| **M0 筑基**（0–3 月） | **5–7 人** | 技术负责人/架构师、后端 ×2、前端 ×1、QA（可兼职）、教研/内容 ×1 | 产品由创始人兼任；先用最小团队验证底座能建起来 |
| **M1 闭环**（3–6 月） | **10–14 人** | + AI 工程师、后端 ×2、前端 ×1、QA 专职、数据工程师、设计师、教研 +1 | 掌握度与个性化进入攻坚，需要算法与数据能力 |
| **M2 增长**（6–12 月） | **20–28 人** | + SRE、安全合规、后端 ×2、前端 ×2、QA +1、产品经理 ×2、内容运营 ×2、用户运营 ×1 | 商业化与增长期，运营与合规成为必需 |
| **M3 规模**（12 月+） | **35 人+** | 按产品线分组，各组补齐 BA/项目经理 | 服务化与多产品线 |

**招聘优先级（M0 前三个人）**：
1. **技术负责人/架构师** —— 底座能不能建起来取决于这个人；
2. **学习引擎后端** —— 掌握度模型是产品核心，也是最难的部分；
3. **全栈/前端** —— 保证主线体验可交付。

> 第四人建议是**教研负责人**：知识点体系是掌握度模型的燃料，没有教研，模型无从落地。

### 2.1 技术负责人 / 架构师

| 项 | 内容 |
|---|---|
| **定位** | 技术方向的最终决策者与质量守门人，对系统可用性、可扩展性、交付效率负总责 |

| **负责模块** | 全局架构；`app/main.py`、`app/database.py`、`app/config.py`、`app/migrations/`；跨域契约；CI/CD 与研发规范；D9（IM/账本）隔离决策 |
| **任职要求** | 8 年以上后端经验，3 年以上技术负责人经历；主导过从单体到模块化的演进（有踩坑经验）；精通 Python/FastAPI 或同等后端栈；熟悉 MySQL 大规模表设计与迁移治理；能判断「什么时候不该拆微服务」；有教育/内容类产品线经验优先；能写代码、能做 Code Review，不是纯管理岗 |
| **产出标准** | 架构决策以 ADR（架构决策记录）沉淀，每个重大决策一篇；域边界与数据所有权文档持续更新；线上 P0 事故有 RCA 报告与改进项闭环 |
| **协作接口** | 向创始人汇报技术风险与资源需求；为各业务组提供架构评审；与产品负责人共同裁定技术可行性；与 SRE 共担可用性指标 |
| **考核指标** | 系统可用性（≥99.9%）；交付周期（需求平均交付时长）；线上缺陷逃逸率；技术债清理进度；关键人才留存 |

## 四、招聘与团队建设建议

### 4.1 招聘顺序（M0 起）

1. **技术负责人/架构师** —— 底座决定上限，且后续招聘需要他把关
2. **学习引擎后端** —— 掌握度模型是核心且最难，招人周期长，尽早启动
3. **平台后端** —— 可观测性与合规机制依赖此人
4. **教研负责人** —— 知识点体系是掌握度模型的燃料，需与引擎同步启动
5. **前端（学生端）** —— 保证体验可交付
6. **全栈/交易后端（M0 后期）** —— 商业化需要支付经验

### 4.2 面试考察重点

| 岗位 | 必考项 | 淘汰信号 |
|---|---|---|
| 技术负责人 | 让候选人现场评审本项目的域划分方案，并提出反对意见 | 只会说「都拆成微服务」；没有从 0 到 1 的经验 |
| 学习引擎后端 | 给出历史答题数据，让其设计掌握度计算方案并说明假设 | 只谈模型不谈可解释性；无法说明如何验证效果 |
| 交易后端 | 设计一个退款流程，考察幂等与对账 | 没处理过重复回调；忽视对账 |
| 测评后端 | 给一道题让其实现判分，考察边界（浮点、中文数字、多解） | 只考虑 happy path |
| AI 工程师 | 让其为「AI 讲题」写 Prompt 并说明如何评测效果 | 只调 Prompt 不做评测；不关心成本 |
| 前端 | 让其现场拆分一段 3,000 行的巨型文件 | 想一次性重写而非渐进拆分 |

### 4.3 团队文化建议

- **无责复盘（Blameless RCA）**：故障复盘对事不对人，否则问题会被隐藏。
- **Owner 意识**：每个域有明确 Owner，出问题找 Owner，不是「大家一起看看」。
- **文档即产出**：没有文档的工作视为未完成（尤其架构决策与指标定义）。
- **质量内建而非靠 QA 兜底**：QA 是门禁，不是清洁工。
- **AI 辅助但要负责**：允许用 AI 生成代码，但提交者对代码质量负全责，且必须能解释每一行。
