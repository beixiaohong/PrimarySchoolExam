## 一、产品定位重构

### 1.1 当前定位的问题

智学学堂现状是「**功能集合体**」——30 个功能模块并列铺开，缺少一条贯穿的主线。用户进来后要自己拼凑学习路径：背单词、做数学、背古诗、刷试卷、养宠物、记账、聊天。

竞品已经给出答案：**主线是「诊-学-练-测」的效果闭环**，其它功能都是围绕这条主线的增强或留存手段。

### 1.2 建议定位

> **一句话定位**：面向小学至初中学生、以「掌握度」为核心的自适应学习平台——让家长看得见孩子「真正掌握了多少」，而不只是「做了多少题」。

**定位拆解**

| 维度 | 定位选择 | 理由 |
|---|---|---|
| 学段 | 小学 1–6 年级为核心，初中 7–9 年级为延伸 | 现有种子数据（小学 1969 词）与出题引擎已覆盖；初中是自然升学延伸，不做高中 |
| 学科 | 数学、语文、英语三科做深 | 与现有强制任务三科体系一致，资源集中 |
| 核心差异化 | **掌握度可视化 + 家长可干预** | 竞品重学生端自动化，家长端多停留在「管控」层面；本产品已有家长密码守卫、任务自定义、补签卡等信任基础，可升级为「科学监督 + 协同干预」 |
| 商业模式 | 免费基础练习 + 订阅会员（AI 与深度学情） | 与行业主流一致，降低决策门槛 |
| 不做 | 社交（IM）、个人账本、游戏化过重 | 与主线无关，冻结并隔离（见总纲判断二） |

### 1.3 用户分层与核心诉求

| 角色 | 核心诉求 | 当前满足度 | 本期重点 |
|---|---|---|---|
| **学生（主用户）** | 做题不难、有人讲、进步看得见、不枯燥 | 🟡 有练习有讲解，无掌握感、无路径感 | 掌握度可视化、学习路径、AI 讲题引导式追问 |
| **家长（付费决策者）** | 知道孩子哪里不会、不用全程陪、效果可信 | 🟠 有任务设置与周报，缺学情洞察 | 学情中心、掌握度报告、干预建议、可信度建设 |
| **老师（M2 引入）** | 批改省力、班级共性错题、针对性讲评 | 🔴 无 | 班级作业批改与高频错题统计（M2 试点） |
| **运营（内部）** | 看得见数据、能干预、能快速验证 | 🟠 有后台看板，无指标体系与实验能力 | 指标树、埋点、A/B 实验、内容运营工具 |
| **教研/内容（内部）** | 内容生产高效、质量可控、能迭代 | 🟠 有采集管线，无标注/审核/版本工作流 | 内容生产流水线与质量抽检 |

## 二、功能优化路线图

### 2.1 M0 筑基（0–3 个月）：把底座补齐

> 原则：**这个阶段几乎不新增面向用户的功能**，全部是「看不见但决定生死」的能力。

| # | 主题 | 关键交付 | 验收标准 | 负责角色 |
|:--:|---|---|---|---|
| M0-1 | **掌握度模型 v1** | 建立「学生 × 知识点」掌握度矩阵；基于答题记录（正确率、用时、最近时间、难度）计算掌握度分值 | 每个学生在每个知识点上有可解释的掌握度分值；知识点覆盖率 ≥ 90%；计算结果可在后台查询 | 学习引擎后端 + 教研 |
| M0-2 | **交易与会员体系 v1（人工支付网关版）** | 商品中心/订单/订阅/权益/对账；**本期不接第三方支付**，采用「用户下单 → 线下支付 → 后台人工置为已支付 → 自动发放权益」；支付网关抽象层预留，未来接入微信/支付宝零改动切换 | 可完成一笔「下单→人工核销→权益到账」全流程；订单状态机完整；人工核销有审批流与操作审计；可对账；权益发放幂等 | 商业化后端 + 产品 |
| M0-3 | **合规底座** | 儿童个人信息处理规则、监护人同意流程、年龄识别、内容安全过滤、等保二级启动、教育 App 备案启动 | 法务/外部顾问评审通过；同意记录可存证可撤回；生成式 AI 输出有安全过滤与标识 | 安全合规 + 后端 |
| M0-4 | **可观测性** | request-id 全链路、结构化日志、核心指标（DAU/答题量/AI 调用与成本/接口 P95/错误率）、告警 | 任一线上问题可在 10 分钟内定位到请求链路；核心指标有看板；P0 告警 5 分钟触达 | SRE/后端 |
| M0-5 | **IM/账本冻结隔离** | 冻结新需求，抽取为独立模块，物理隔离依赖 | 主应用可通过配置关闭这两块；学习主线代码不再引用其模型 | 架构师 |
| M0-6 | **测试补齐** | 主线关键域（掌握度、交易、AI）单测覆盖；建立 CI 流水线 | 关键域覆盖率 ≥ 80%；CI 全绿成为合并前置条件 | QA + 全体 |

### 2.2 M1 闭环（3–6 个月）：让「诊-学-练-测」跑起来

| # | 主题 | 关键交付 | 验收标准 | 负责角色 |
|:--:|---|---|---|---|
| M1-1 | **诊断测评** | 入学诊断 + 单元诊断；以少量题目快速定位薄弱知识点 | 20 题内定位出 Top5 薄弱知识点，与全量测评结果相关性 ≥ 0.7 | 教研 + 学习引擎 |
| M1-2 | **个性化学习路径** | 基于掌握度 + 遗忘曲线 + 知识点依赖，生成每日学习路径 | 路径可解释（为什么推这道题）；实验组掌握度提升显著优于规则组 | 学习引擎 + 数据 |
| M1-3 | **AI 讲题升级** | 从「给解析」升级为「引导式追问」：分步提示 → 追问薄弱点 → 同类题巩固 | 学生看完讲解后同类题正确率提升 ≥ 15%；AI 输出 100% 过安全过滤 | AI 工程师 + 教研 |
| M1-4 | **家长学情中心** | 掌握度热力图、周/月学情报告、薄弱点归因、可执行的干预建议（而非仅数据罗列） | 家长周报打开率 ≥ 40%；报告含至少 1 条可执行建议 | 产品经理 + 前端 |
| M1-5 | **内容生产流水线** | 采集 → 清洗去重 → 知识点标注 → 审核 → 入库 → 版本发布 → 抽检 | 单题入库全链路可追踪；抽检合格率 ≥ 98%；内容版本可回滚 | 内容运营 + 后端 |
| M1-6 | **运营后台** | 用户分层、活动配置、优惠券、公告定向推送、内容上下线、数据看板 | 运营可自助完成一次活动配置与投放，无需研发介入 | 平台后端 + 产品 |
| M1-7 | **AI 成本治理** | 模型路由策略、缓存复用、配额与限流、成本看板、输出质量评测集 | 单位答题 AI 成本下降 ≥ 30%；有回归评测集守护质量 | AI 工程师 |

### 2.3 M2 增长（6–12 个月）

| # | 主题 | 关键交付 | 验收标准 |
|:--:|---|---|---|
| M2-1 | **AI 学习伙伴** | 具备情绪感知与动机激发的伴学智能体；明示 AI 身份、可关闭情感模式 | 日均对话轮次 ≥ 5；家长可管控；有安全护栏 |

## 三、商业化设计

### 3.1 现状与问题

- 支付/订单/订阅端点数：**0**。
- 钻石充值依赖 `/api/diamond/recharge/config` 返回的静态二维码，**用户转账后靠运营肉眼核对聊天记录/流水再手动加钻**——无订单、无状态机、不可对账、有资金风险。
- VIP 仅能由管理员在后台手动开关（`/api/admin/vip`），无自助购买、无权益定义、无到期管理、无流水。

### 3.2 建议的商业模式

**主模型：免费 + 订阅会员**（与行业主流一致）

| 层级 | 价格参考（竞品区间） | 权益设计 |
|---|---|---|
| 免费 | 0 | 基础练习（每日额度）、基础错题本、基础任务、有限 AI 调用（如 5 次/日） |
| VIP | 参考竞品：月 25–30 / 季 88 / 年 268–398 元 | 无限 AI 讲解、完整学情报告、个性化学习路径、诊断测评、专项练习库、优先客服 |
| SVIP / 家庭版 | 参考竞品：年 298 元区间 | VIP 全部 + 家长深度报告、多孩管理、老师答疑通道、导出打印 |

**辅模型**

1. **钻石内购**（保留现有体系）：按次付费补充，覆盖重度 AI 使用；需改造为正规支付订单而非人工转账。
2. **B 端机构订阅**（M2）：按班级/学校订阅，老师端能力打包。
3. **内容增值**（M3）：专项练习册、真题卷包、打印服务。

### 3.3 本期支付策略：**人工支付网关（Manual Payment Gateway）**

> **决策（2026-09-02 产品评审定案）**：M0 / M1 阶段**不接入微信支付、支付宝等第三方支付接口**。用户可正常下单，支付环节走「**线下转账 + 后台人工核销**」；待支付通道正式对接后，再实现自动化到账。

**为什么这么定**

| 理由 | 说明 |
|---|---|
| 资质与周期 | 微信支付/支付宝商户号需企业主体、教育类资质、费率谈判，开通周期以周计，会阻塞 M0 交付 |
| 合规优先级 | 未成年人消费涉及监护人同意与退款要求，先跑通业务闭环与审计，再叠加资金通道，风险更可控 |
| 验证价值 | M0 阶段真实付费用户量小，先验证「定价是否合理、权益是否有人买」，比先做支付通道更有价值 |
| 成本 | 省去验签、异步回调、重复回调、对账文件解析等一整套复杂度，M0 可聚焦订单与权益 |

**业务流程（人工支付网关 v1）**

```
① 用户在前端选择商品（会员 SKU / 钻石包）
        ↓
② 创建订单 → 状态 PENDING_PAYMENT，展示收款二维码 + 订单号 + 应付金额 + 付款备注格式
        ↓
③ 用户线下扫码/转账支付，按要求填写备注（订单号后 6 位）
        ↓
④ 运营在后台「待核销订单」列表中找到该订单，
   核对实收金额与付款流水号后，点击【确认收款】
        ↓
⑤ 系统校验（金额一致 + 操作人有核销权限 + 订单处于待支付 + 幂等键未使用）
   → 订单置为 PAID（记录 pay_channel=MANUAL、核销人、核销时间、外部流水号、凭证截图）
        ↓
⑥ 权益发放引擎按商品绑定的权益模板发放（会员时长 / 钻石 / 卡券），写入发放流水
        ↓
⑦ 订单置为 FULFILLED，通知用户，记录埋点 order_paid
```

**必须与人工核销配套的机制（缺一不可）**

| 机制 | 要求 |
|---|---|
| **权限与审批** | 核销操作需独立权限点 `order:confirm_payment`；单笔金额超过阈值（建议 500 元）需二级审批 |
| **操作审计** | 每次核销写 `admin_operation_logs`（操作审计）：操作人、时间、订单号、实收金额、外部流水号、凭证、IP、UA；不可删除、不可修改 |
| **幂等** | 订单号 + 幂等键（`idempotency_key`）双保险；同一外部流水号不可用于两笔订单；重复点击只发放一次权益 |
| **对账** | 每日出「人工核销日报」：核销笔数/金额、待核销超 24h 单数、异常金额单数；运营负责人签字确认 |
| **超时关单** | 待支付订单 24 小时未核销自动关单（CLOSED），释放库存/名额 |
| **撤销与退款** | 支持「核销错误」的冲正（REVERSED）与「用户退款」（REFUNDED），均需审批；退款需扣回已发权益（钻石可为负余额时冻结账号） |
| **资金风险兜底** | 人工核销期间每日核销总额设上限；收款账户与运营人员职责分离（收款人 ≠ 核销人，尽量） |

**支付网关抽象层（为未来自动化到账预留）**

```python
class PaymentGateway(Protocol):          # 抽象接口，业务层只依赖它
    def create_payment(self, order) -> PaymentIntent: ...
    def query_payment(self, order) -> PaymentStatus: ...
    def refund(self, order, amount) -> RefundResult: ...
    def verify_callback(self, payload, headers) -> CallbackEvent: ...

class ManualGateway(PaymentGateway):     # 本期实现：无外部调用
    def create_payment(self, order): return PaymentIntent(qr_url=..., memo=order.no[-6:])
    def query_payment(self, order):  return order.status  # 以人工核销结果为准

class WechatPayGateway(PaymentGateway):  # 未来实现：不动业务代码
    ...
```

- 业务层（订单服务、权益发放）**只依赖 `PaymentGateway` 接口**，不感知具体实现。
- 未来接入微信/支付宝时：新增一个实现类 + 在配置里切换 `PAYMENT_GATEWAY=wechat`，**订单服务、权益发放、对账报表零改动**。
- 状态机统一：`PENDING_PAYMENT → PAID → FULFILLED`，人工与自动两条路径共用同一套状态机与幂等逻辑——这是「零改动切换」的前提。
- 命名对齐：本方案 `PaymentGateway` 即 `app/domains/commerce/contracts.py` 规划的域契约 `PaymentService.pay()` 的内部策略接口，两者语义一致，开发时以 `contracts.py` 的 `PaymentService` 为对外收口入口。
- 命名对齐：本方案 `PaymentGateway` 即 `app/domains/commerce/contracts.py` 规划的域契约 `PaymentService.pay()` 的内部策略接口，两者语义一致，开发时以 `contracts.py` 的 `PaymentService` 为对外收口入口。

**未来切换自动化到账的验收清单（M1-M2 触发）**

1. 商户号与资质齐备（企业主体、教育类目、费率确认）。
2. `PaymentGateway` 新实现通过沙箱全用例（下单/支付/回调/退款/重复回调/验签失败）。
3. 灰度：先 5% 订单走自动通道，其余走人工，双轨对账 7 天零差异。
4. 全量切换后，人工核销入口降级为「补单/异常单」专用，保留审计轨迹。

### 3.4 交易体系必须有的模块

| 模块 | 说明 | 优先级 | 本期范围（人工支付网关版） |
|---|---|---:|---|
| 商品中心 | 会员 SKU、钻石包、权益模板、价格与促销 | P0 | ✅ 全量做（含权益模板绑定） |
| 订单 | 状态机（待支付→已支付→已履约→已取消/已退款/已冲正）、幂等、超时关单 | P0 | ✅ 全量做 |
| 支付 | 支付网关抽象层 + `ManualGateway`（人工核销）；第三方接入**不在本期** | P0 | ⚠️ 仅做抽象层与人工实现 |
| 对账 | 日终人工核销日报、差异告警、补单入口 | P0 | ✅ 做（对账对象为「订单 vs 人工核销记录 vs 银行流水」三方） |
| 订阅 | 周期管理、到期降级、宽限期；**自动续费不在本期**（人工续费，到期前提醒 + 用户重新下单） | P0 | ⚠️ 做周期与降级，不做自动续费扣款 |
| 权益 | 权益发放与核销、额度控制、灰度、幂等 | P0 | ✅ 全量做 |
| 发票与退款 | 电子发票、退款流程 | P1 | 🔻 降为 P2（本期仅做退款冲正，不做发票） |
| 风控 | 退款滥用识别、异常支付拦截 | P1 | ⚠️ 本期仅做「异常核销拦截」（金额不符、流水号复用、高频核销） |

> **硬要求（不因人工支付而降低）**：交易链路必须有幂等设计、完整流水、权限审批、可追溯对账。这是资金合规底线，也是未来切换自动支付时不被推翻的前提。
>
> **未成年人相关**：会员/钻石购买需监护人同意确认（勾选 + 记录），退款政策需在下单页明示。人工核销阶段更要留存完整证据链，避免纠纷时无据可依。

## 四、内容体系设计

### 4.1 现状

| 采集管线 | 第一试卷网日采约 200 份（含答案 AI 补全） |
| 题库 | `questions`（出题式）与 `papers`/`paper_questions`（采集式）双轨解耦——**架构正确** |
| 差距 | 与竞品亿级题库、500 万课时视频相比是量级差距；且**缺知识点标注体系**（M0-1 的前置条件） |

### 4.2 内容战略：不拼题量，拼「标注质量 + 与本地教材匹配」

与头部拼题量没有胜算。可行路径：

1. **知识点体系先行**：建立覆盖小学 1–6 年级 + 初中 7–9 年级三科的知识点树（K-12 学科知识图谱），每题必须挂载知识点。这是掌握度模型与个性化推荐的**燃料**。
2. **区域化教材匹配**：深度绑定 2–3 个主流教材版本（人教/北师大/苏教）+ 重点区域，做透「本地化同步」，而非全国撒网。
3. **采集 + 生成 + 教研三源供给**：
   - 采集：现有管线（试卷）；
   - 生成：自研出题引擎（数学已 13 子包，英语/语文可扩）；
   - 教研：人工编写精品题与讲解。
4. **质量闭环**：AI 生成的题目必须过「可解性校验 + 答案校验 + 教研抽检」三关。项目历史上已有 8 次判分准确性修复（浮点舍入、中位数奇偶、中文数字容差等），说明**自动化校验必须常态化**，不能靠用户反馈驱动。

### 4.3 内容生产流水线

```
采集/生成 → 去重清洗 → OCR/结构化 → 知识点标注 → 答案与解析校验
   → 教研审核（抽检）→ 入库（版本化）→ 线上生效 → 效果回流（错误率/举报/申诉）→ 下线与修订
```

关键控制点：
- **每题可追溯**：来源、标注人、审核人、版本、生效时间。
- **质量抽检**：新入库内容抽检比例 ≥ 5%，合格率 < 98% 触发批次回退。
- **申诉驱动修订**：`/api/appeal` 已有答题申诉，应把申诉数据作为内容质量的**自动信号源**，高频申诉题自动进入复核队列（现已有 `judge_review_issues`、`content_reviews` 表，需打通）。

## 五、AI 能力策略

### 5.1 现状风险

- 三链路 fallback（智谱免费 → Relay → DeepSeek），但**免费链余额已耗尽/限流，实际仅 DeepSeek 可用**——单点依赖。
- 无输出质量评测集、无成本看板、无缓存复用。
- 生成式 AI 输出需满足《可能影响未成年人身心健康的网络信息分类办法》要求。

### 5.2 策略

| 方向 | 措施 |
|---|---|
| **模型路由** | 按任务类型路由：轻量任务用便宜模型（判选择/填空），深度讲解用强推理模型；建立多供应商抽象层，任一供应商故障可切换 |
| **成本治理** | 语义缓存复用、Prompt 精简、批量合并、配额与限流、单位成本看板 |
| **质量守护** | 建立回归评测集（每学科 ≥ 200 题，人工标注标准答案与讲解要点），每次 Prompt/模型变更必须跑评测 |
| **安全护栏** | 输入侧敏感过滤 + 输出侧安全审核 + 兜底模板；AI 身份明示；家长可关闭 |
| **教育专业性** | 借鉴头部「通用推理模型 + 教育专业约束」双层设计：推理模型负责解题，教育规则层负责分步引导与认知规律 |

## 六、指标体系

### 6.1 现状

`metric`/`monitor` 端点为 0，无埋点体系、无指标定义、无看板（后台仅有基础 `dashboard`/`analytics`）。

### 6.2 北极星指标

> **周活跃 learning 用户的知识点掌握度提升量**

选择理由：它同时反映「用户活跃」「学习发生」「效果真实」，且直接对齐产品定位。单一 DAU 会诱导做无用功能，单一做题量会诱导刷量。

### 6.3 分层指标树

| 层级 | 指标 | 用途 |
|---|---|---|
| 北极星 | 周活跃用户掌握度提升量 | 战略健康度 |
| 获客 | 新增注册、渠道分布、获客成本、激活率（完成首次诊断） | 增长 |
| 活跃 | DAU/WAU/MAU、DAU/MAU、次日/7 日/30 日留存、人均学习时长 | 留存健康 |
| 学习 | 日均答题量、知识点覆盖率、诊断完成率、路径完成率、错题重做正确率 | 核心价值交付 |
| 效果 | 掌握度提升速率、薄弱点转化率、同类题正确率提升 | 效果证明 |
| AI | 调用量、成功率、P95 延迟、单位成本、讲解后正确率提升 | 成本与质量 |
| 商业 | 付费转化率、ARPU、续费率、退款率、LTV/CAC | 商业化健康 |
| 质量 | 崩溃率、接口错误率、P95 延迟、内容申诉率、判分争议率 | 技术健康 |
| 合规 | 监护人同意率、内容安全拦截量、投诉响应时长 | 合规健康 |

### 6.4 埋点要求

- 统一埋点 SDK 与事件命名规范（对象_动作_属性）。
- 关键漏斗必须可下钻到用户维度（用于问题排查与用户研究）。
- 事件字典由数据负责人维护，变更需评审——**埋点漂移是数据质量的头号杀手**。

## 七、优先级决策原则

当资源冲突时，按以下顺序裁决：

1. **合规 > 一切**。任何合规红线问题无条件优先。
2. **效果闭环 > 功能数量**。能提升掌握度的事优先于增加新模块。
3. **主线 > 外围**。学习主线（诊断-学-练-测）优先于社交、工具、装饰性功能。
4. **可衡量 > 凭感觉**。无法定义成功指标的功能，暂缓。
5. **可回滚 > 快速上线**。涉及数据结构与内容生效的变更，必须有回滚方案。

## 八、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 合规处罚（未成年人信息/内容安全） | 下架、罚款、品牌损失 | M0 阶段完成合规底座，外部法务评审，年度审计机制 |
| AI 供应商单点故障/涨价 | 成本失控、服务不可用 | 多供应商抽象、配额限流、缓存、成本看板、降级方案 |
| 内容质量事故（错题/争议答案） | 信任崩塌，家长流失 | 三关校验 + 抽检 + 申诉驱动复核 + 快速下线能力 |
| 掌握度模型不准确 | 推荐失灵，产品核心卖点落空 | 小步验证：先离线回测历史数据，再小流量实验，最后全量 |
| 商业化和体验冲突 | 付费墙激怒用户，留存下降 | 免费额度足够完成基础学习闭环；付费点为「深度洞察与效率」而非「基础能力」 |
| 团队扩张导致质量塌方 | 缺陷率上升、交付变慢 | 流程规范（见 `04-研发流程规范.md`）与按域负责制（见 `03-研发组织与岗位说明书.md`） |
| **人工核销出错/内控失效**（误核销、重复发放、虚假核销） | 资金损失、纠纷、审计不通过 | 核销权限独立 + 大额二级审批 + 强制凭证上传 + 流水号唯一约束 + 全量审计日志 + 每日核销日报 + 收款/核销职责分离 |
| 人工核销成为规模化瓶颈 | 订单积压、用户等待久、体验差 | 明确「人工核销为过渡态」：设定切换自动支付的触发条件（日核销单量 > N 或 商户号落地后 30 天内）；核销后台做批量操作与快捷搜索 |
| 支付通道切换时订单模型被推翻 | 返工、数据迁移风险 | 本期即按 `PaymentGateway` 抽象设计，人工与自动共用状态机与幂等键；上线前做「自动通道沙箱回灌」验证 |
