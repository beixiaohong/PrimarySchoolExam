## 一、现状架构诊断

### 1.1 架构形态

**单体 FastAPI 应用**，38 个路由文件 + 7 个路由子包，全部共享同一个 MySQL 库与同一套 `SessionLocal`。优势是开发效率高（一个人 + AI 可以快速堆功能），问题是**没有域边界**：

> 本节描述的是 **S1-R 搬迁前**的现状（历史快照）。该结构已按 §四 S1 重组为 `app/domains/<域>/{routers,services}/`；
> `app/routers/` 下仅余后台共享装配包 `admin/`，`app/services/` 仅余多域共用的 `semester.py`；
> `app/models/`、`app/schemas/`、`app/database.py`、`app/config.py`、`app/migrations/` 按修订 3 留作**共享内核**。

- 任意路由文件可以直接 import 任意模型、任意服务；
- 跨域数据通过直接查表获得，而非通过接口；
- 一个 Session 贯穿整个请求，`get_db` 只 close 不 commit（历史上曾因持连做外部调用导致全站卡死）。

### 1.2 具体病灶

| # | 问题 | 证据 | 后果 |
|:--:|---|---|---|
| 1 | 无请求链路追踪 | `main.py` 无任何中间件，无 request-id | 线上问题只能翻文本日志定位 |
| 2 | 无全局异常处理 | `main.py` 无 `exception_handler` | 未捕获异常返回原始堆栈或 500，错误码不统一 |
| 3 | 域边界缺失 | 路由文件可直接跨 import | 改动一处可能波及无关模块，评审无法界定影响面 |
| 4 | 无关业务占据主干 | `im.py` 1,251 行 + `ledger.py` 1,086 行，合计 71 端点 | 19% 代码量为维护负担，且零测试覆盖 |
| 5 | 前端逻辑单点 | `appOptions.js` 3,643 行 | 任何前端改动都是高风险 |
| 6 | 无 CI | 仓库无流水线配置 | 质量依赖人工执行测试，易漏 |
| 7 | 迁移靠人工 | `qb_versions/` 脚本手动传线上执行 | 无评审、无回滚、无审计 |
| 8 | 静态资源本地落盘 | `output/` 存放试卷/图片/音频 | 无法水平扩展，备份与清理困难 |
| 9 | 定时任务靠 cron + 自研 scheduler | `tools/scheduler.py` + crontab 15 分钟轮询 | 无失败重试可视化、无并发控制、无告警 |

## 二、拆分原则与判据

### 2.1 三条原则

1. **先做模块化单体，不要直接微服务。**
   377 个端点、85 张表，团队规模在 20 人以下时拆微服务，只会把「代码耦合」变成「分布式耦合」，调试成本翻倍。**先在单体内划清域边界，等边界稳定了再物理拆分。**

2. **按「变更频率 + 资源特性 + 故障域」判断该不该独立部署，而不是按「业务名词」。**
   - 变更频率高且独立的（AI 网关）：适合独立；
   - 资源特性特殊的（离线采集、CPU/内存密集）：适合独立；
   - 故障必须隔离的（支付）：适合独立；
   - 只因「名字像个服务」而拆的（用户服务、订单服务）：**不拆**。

3. **数据所有权先于代码拆分。**
   每张表必须有且仅有一个归属域。跨域访问只能通过域提供的接口，禁止跨域 JOIN。这条不落实，任何代码拆分都是假的。

### 2.2 拆分判据表

| 判据 | 满足即倾向独立部署 | 本项目命中 |
|---|---|---|
| 资源特性差异 | CPU/内存/IO 特征与主应用显著不同 | AI 网关（长耗时、外部依赖）、内容处理（离线重计算） |
| 故障域隔离 | 该模块故障不应拖垮主流程 | 支付/交易、AI 网关（需熔断）、通知服务 |
| 变更频率 | 迭代节奏与主线不同步 | 内容采集管线、运营后台 |
| 伸缩需求 | 需要独立扩容 | AI 网关、内容处理 |
| 合规边界 | 数据需独立存储与审计 | 交易（资金流水）、未成年人个人信息 |
| 团队边界 | 独立小组独立交付 | 各业务域（但不足以支撑独立部署） |

#### S1-R 补充：表级数据所有权护栏延后到 S1.5（实测理由）

S1-4 原设想还包含「禁止跨域 import `app.models` 中他域归属表」，实测**在 S1 无法作硬门禁**，四条理由（取证见 `.importlinter` 契约 3 注释与 `docs/data-ownership.md` §6.4）：

1. **粒度不匹配**：grimp 的依赖图是模块级的，分不清 `from app.models.parent import ParentTaskSettings`（D5 自有）与 `ParentMessage`（D6）；
2. **模型文件本身跨域混合**：40 个模型文件里 6 个横跨 2-3 个域（`user.py`=D1+D7、`admin.py`=D1+D8、`parent.py`=D1+D5+D6、`ai_usage.py`=D7+D8、`classical.py`=D2+D4、`sprint4.py`/`middle.py`=D2+D3）；
3. **存量规模**：`app/domains/**` 内 `app.models.*` 的 import 共 316 行，收敛为 101 组（域→模型文件）、分布 102 个文件，按文件粒度设禁会误伤合法的自有表访问；
4. **裸 SQL 盲区**：7 处 `text("...")` 裸 SQL（含 D8 `platform/services/ai.py:54` 直读 D7 的 `vip_users`）与 §6.3 的 D9 穿透，模块级规则完全看不见。

因此 S1 的执行载体是 **`docs/data-ownership.md` 登记表 + 人工评审 + 域级静态门禁**；表级 forbidden 契约已以注释形态与启用模板留存在 `.importlinter`，按该文件 §7 的 6 步在 S1.5 打开。

  > 现存跨域表访问事实已全部登记：高扇出表 TOP6（`users`/`study_errors` 各 7 域）、7 处裸 SQL、D8→D9 数据层穿透。

### 6.2 迁移纪律（针对现有自建迁移系统）

现有 56 个脚本（001–025 为 SQLite 历史基线，026+ 幂等执行）可用，但需加纪律：

| 规则 | 说明 |
|---|---|
| 一迁移一 PR | 迁移脚本不与业务代码混在一起提交 |
| 必须幂等 | 重复执行不报错、不产生副作用（现有 026+ 已做到，需保持） |
| 必须可回滚 | 每个迁移附回滚脚本或明确声明不可回滚及理由 |
| 必须评审 | 大表变更（>100 万行）需负责人评审，并给出执行窗口与影响评估 |
| 禁止运行时 DDL | 迁移只能在发布流程中执行，禁止应用在运行时自动改表（`_ensure_column` 这类兜底需逐步收敛） |
| 历史基线归档 | 001–025 在 MySQL 下本就预置为已执行，归档到 `versions/archive/`，避免误导 |

## 八、拆分过程中的红线

1. **搬迁不改逻辑**：S1 阶段只移动文件与调整 import，禁止顺手重构。混在一起做，出问题无法定位是搬迁还是重构导致。
2. **端点快照零差异**（修订 2）：搬迁前后各跑一次 `.venv\Scripts\python.exe tools\endpoint_snapshot.py <输出文件>`，与仓库根 `endpoint_baseline.txt` **逐行 diff 必须为空**（口径 **382 行 = 377 HTTP + 4 MOUNT + 1 WebSocket**，含 `/health`、`/`、`/admin` 等系统端点）。原文「必须仍是 377」只比总数，发现不了同数量的一增一减。
3. **测试必须实跑全绿**（修订 2）：每完成一个域搬迁，全量 **130** 用例必须**实跑**通过（**0 skip / 0 error**）才继续。原文「全量 124 用例必须通过」是假门禁：测试库不可用时 conftest 会整体 skip，「全绿」退化为「全 skip 仍算通过」。用例数 124→130 为恢复测试库后的实测口径。
4. **禁止跨域新耦合**：搬迁期间新产生的跨域调用，一律走契约接口，不留「临时直连」的技术债。
   > **S1-R 已落地并强制**：存量 70 行跨域 import 已改指目标域 `contracts.py`（44 文件），服务调用收口到
   > `DiamondService`/`PetService`/`GrowthTreeService`/`TaskService`（22 文件 39 处）；`.importlinter` + pre-commit
   > 钩子在 **commit 时刻**强制（人为构造违规 import 已验证被拒）。
   > **残留 2 类（登记待 S1.5）**：① 裸 SQL 跨域读（D8 `platform/services/ai.py:54` 直读 D7 `vip_users`）；
   > ② D8 `admin_panel.py` 直读 D9 的 7 张表做 `count()` 统计。两者都走共享内核 `app.models`，模块级护栏看不见。
5. **前端同理**：`appOptions.js` 拆分时按视图切分，一次一个视图，切完跑通再切下一个。
