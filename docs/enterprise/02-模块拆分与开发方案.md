## 一、现状架构诊断

### 1.1 架构形态

**单体 FastAPI 应用**，38 个路由文件 + 7 个路由子包，全部共享同一个 MySQL 库与同一套 `SessionLocal`。优势是开发效率高（一个人 + AI 可以快速堆功能），问题是**没有域边界**：

- 任意路由文件可以直接 import 任意模型、任意服务；
- 跨域数据通过直接查表获得，而非通过接口；
- 一个 Session 贯穿整个请求，`get_db` 只 close 不 commit（历史上曾因持连做外部调用导致全站卡死）。

### 1.2 具体病灶

| # | 问题 | 证据 | 后果 |
|:--:|---|---|---|
| 1 | 无请求链路追踪 | `main.py` 无任何中间件，无 request-id | 线上问题只能翻文本日志定位 |
| 2 | 无全局异常处理 | `main.py` 无 `exception_handler` | 未捕获异常返回原始堆栈或 500，错误码不统一 |
| 3 | 域边界缺失 | 路由文件可直接跨 import | 改动一处可能波及无关模块，评审无法界定影响面 |
| 4 | 无关业务占据主干 | `im.py` 1,251 行 + `ledger.py` 1,086 行，合计 71 端点 | 19% 代码量为维护负担，且零测试覆盖 |
| 5 | 前端逻辑单点 | `appOptions.js` 3,643 行 | 任何前端改动都是高风险 |
| 6 | 无 CI | 仓库无流水线配置 | 质量依赖人工执行测试，易漏 |
| 7 | 迁移靠人工 | `qb_versions/` 脚本手动传线上执行 | 无评审、无回滚、无审计 |
| 8 | 静态资源本地落盘 | `output/` 存放试卷/图片/音频 | 无法水平扩展，备份与清理困难 |
| 9 | 定时任务靠 cron + 自研 scheduler | `tools/scheduler.py` + crontab 15 分钟轮询 | 无失败重试可视化、无并发控制、无告警 |

## 二、拆分原则与判据

### 2.1 三条原则

1. **先做模块化单体，不要直接微服务。**
   377 个端点、85 张表，团队规模在 20 人以下时拆微服务，只会把「代码耦合」变成「分布式耦合」，调试成本翻倍。**先在单体内划清域边界，等边界稳定了再物理拆分。**

2. **按「变更频率 + 资源特性 + 故障域」判断该不该独立部署，而不是按「业务名词」。**
   - 变更频率高且独立的（AI 网关）：适合独立；
   - 资源特性特殊的（离线采集、CPU/内存密集）：适合独立；
   - 故障必须隔离的（支付）：适合独立；
   - 只因「名字像个服务」而拆的（用户服务、订单服务）：**不拆**。

3. **数据所有权先于代码拆分。**
   每张表必须有且仅有一个归属域。跨域访问只能通过域提供的接口，禁止跨域 JOIN。这条不落实，任何代码拆分都是假的。

### 2.2 拆分判据表

| 判据 | 满足即倾向独立部署 | 本项目命中 |
|---|---|---|
| 资源特性差异 | CPU/内存/IO 特征与主应用显著不同 | AI 网关（长耗时、外部依赖）、内容处理（离线重计算） |
| 故障域隔离 | 该模块故障不应拖垮主流程 | 支付/交易、AI 网关（需熔断）、通知服务 |
| 变更频率 | 迭代节奏与主线不同步 | 内容采集管线、运营后台 |
| 伸缩需求 | 需要独立扩容 | AI 网关、内容处理 |
| 合规边界 | 数据需独立存储与审计 | 交易（资金流水）、未成年人个人信息 |
| 团队边界 | 独立小组独立交付 | 各业务域（但不足以支撑独立部署） |

## 四、三阶段拆分路径

### 阶段 S1：模块化单体（M0，0–3 个月）

**目标**：代码不动、边界先立。不改部署形态，只建立纪律。

| 步骤 | 动作 | 验收 |
|---|---|---|
| S1-1 | 建立 `app/domains/{identity,content,assessment,engine,engagement,family,commerce,platform}/` 目录骨架，每个域含 `router/`、`service/`、`models/`、`schemas/`、`contracts.py` | 目录就位，README 写明职责与边界 |
| S1-2 | 按域迁移现有路由与服务文件（**只移动，不重写**） | 全部 124 用例通过，端点总数仍为 377 |
| S1-3 | 每个域导出**显式契约**（`contracts.py`），定义对外可用的服务方法签名 | 契约文件评审通过 |
| S1-4 | 引入静态检查：禁止跨域 import（`import-linter` 或自定义 flake8 插件），CI 强制 | CI 拦截违规 import |
| S1-5 | 表归属登记（`docs/data-ownership.md`），每张表标注归属域 | 85 张表全部登记，无悬空 |
| S1-6 | 冻结 D9，抽取为独立子包并加开关 | 主应用可关闭 D9 正常启动 |

> **关键纪律**：S1 期间**禁止新功能开发**，只做搬迁与补测试。搬迁本身不产生用户价值，但它是后续一切的前提。

### 阶段 S2：抽出 3 个独立服务（M1–M2，3–9 个月）

按判据表，首批独立部署的三个候选：

| 服务 | 理由 | 边界 | 数据 |
|---|---|---|---|
| **AI 网关服务** | 长耗时、外部依赖、需限流熔断、成本敏感、变更频繁 | 统一的模型路由、计费、缓存、安全护栏、评测 | `ai_usage_log` 迁出；`diamond` 计费通过 D7 接口 |
| **内容处理服务** | 离线重计算（采集、解析、OCR、标注）、资源密集、失败不应影响在线 | 采集 → 解析 → 标注 → 校验 → 入库 | `papers` `paper_questions` 归属，通过消息/任务队列通知主应用 |
| **通知推送服务** | 故障域隔离、第三方依赖多（短信/推送/邮件） | 统一触达通道、模板、频控、送达回执 | `notifications` |

**配套基建（S2 前置）**：消息队列（Redis/RabbitMQ）、对象存储、任务队列、服务间认证、链路追踪。

### 阶段 S3：深度服务化（M2–M3，按需）

仅当**团队规模 > 20 人**且**该域迭代节奏明显独立**时才继续拆。优先候选：交易服务（合规与资金隔离）、IM（若保留）。

> **反模式警告**：不要因为「微服务听起来先进」而拆。本项目 377 端点在 20 人团队下，模块化单体 + 3 个独立服务是更优解。

## 五、技术栈升级清单

| 领域 | 现状 | 升级项 | 优先级 |
|---|---|---|---|
| 请求链路 | 无中间件、无异常处理 | request-id 中间件 + 全局异常处理器 + 统一错误码 + 结构化日志 | **P0** |
| 可观测性 | 1 个硬编码 health、文本日志 | 指标采集（Prometheus）+ 日志聚合 + 链路追踪 + 告警规则 + 真实就绪探针（查 DB） | **P0** |
| CI/CD | 无 | 流水线：lint → 类型检查 → 单测 → 集成测试 → 构建 → 部署；合并前置门禁 | **P0** |
| 配置与密钥 | `.env` 文件 | 密钥管理（Vault/云 KMS）、配置分级、禁止密钥入日志与代码库 | **P0** |
| 数据访问 | 共享 Session，跨域直查 | 域内 Repository、跨域走契约、慢查询监控、连接池治理（现有参数保留） | P0 |
| 缓存 | 无 | Redis：热点缓存、幂等键、限流、会话黑名单 | P1 |
| 异步任务 | cron + `tools/scheduler.py` | 任务队列（Celery/Arq），支持重试、并发控制、失败告警、可视化 | P1 |

## 六、数据库与迁移策略

### 6.1 数据所有权

- 每张表**有且仅有一个归属域**（登记在 `docs/data-ownership.md`）。
- 跨域**禁止 JOIN、禁止直接 import 模型**；只能通过域契约接口。
- 现有 `db_im_*` / `db_ledger_*` 前缀是好实践，新表应延续「域前缀」命名。

### 6.2 迁移纪律（针对现有自建迁移系统）

现有 56 个脚本（001–025 为 SQLite 历史基线，026+ 幂等执行）可用，但需加纪律：

| 规则 | 说明 |
|---|---|
| 一迁移一 PR | 迁移脚本不与业务代码混在一起提交 |
| 必须幂等 | 重复执行不报错、不产生副作用（现有 026+ 已做到，需保持） |
| 必须可回滚 | 每个迁移附回滚脚本或明确声明不可回滚及理由 |
| 必须评审 | 大表变更（>100 万行）需负责人评审，并给出执行窗口与影响评估 |
| 禁止运行时 DDL | 迁移只能在发布流程中执行，禁止应用在运行时自动改表（`_ensure_column` 这类兜底需逐步收敛） |
| 历史基线归档 | 001–025 在 MySQL 下本就预置为已执行，归档到 `versions/archive/`，避免误导 |

### 6.3 大表与增长预估

| 表 | 增长特性 | 策略 |
|---|---|---|
| `ai_usage_log` | 随 AI 调用线性增长 | 按月分区，冷数据归档 |
| `events`（新建埋点） | 海量 | 分区 + 保留策略（明细 90 天，聚合永久） |
| `attempt_answers` | 随答题量增长 | 分区 + 定期归档 |
| `daily_tasks` | 随用户 × 天数增长 | 历史数据按年归档 |

## 八、拆分过程中的红线

1. **搬迁不改逻辑**：S1 阶段只移动文件与调整 import，禁止顺手重构。混在一起做，出问题无法定位是搬迁还是重构导致。
2. **端点总数不变**：搬迁前后各跑一次端点统计（命令见 `PROJECT_STRUCTURE.md` 口径自检），必须仍是 377（或明确的增减理由）。
3. **测试必须全绿**：每完成一个域搬迁，全量 124 用例必须通过才继续。
4. **禁止跨域新耦合**：搬迁期间新产生的跨域调用，一律走契约接口，不留「临时直连」的技术债。
5. **前端同理**：`appOptions.js` 拆分时按视图切分，一次一个视图，切完跑通再切下一个。
