## 2. 术语表

| 术语 | 定义 |
|---|---|
| **知识点（KP, Knowledge Point）** | 学科知识体系中的最小可评估单元，如「分数加减法」「一般现在时」。系统内对应 `knowledge_points` 表的一条记录 |
| **掌握度（Mastery）** | 某学生在某知识点上的掌握程度量化分值，取值 0–100，由答题记录加权计算 |
| **掌握度矩阵** | 「学生 × 知识点」的二元掌握度集合，是个性化推荐与学情报告的数据基础 |
| **诊断测评** | 以少量题目快速定位薄弱知识点的测评方式，区别于完整单元测试 |
| **学习路径** | 基于掌握度、遗忘曲线、知识点依赖关系生成的每日学习任务序列 |
| **人工支付网关（Manual Payment Gateway）** | 本期支付方案：用户下单后通过线下转账支付，运营在后台人工核实收款并置订单为已支付，系统随后自动发放权益 |
| **核销（Confirm Payment）** | 运营在后台将某笔待支付订单确认为「已收到款项」的操作 |
| **冲正（Reverse）** | 因核销错误而撤销该次核销的操作，与用户发起的「退款」区分 |
| **权益（Benefit）** | 购买商品后获得的实际利益（会员时长、钻石、卡券），由权益模板定义 |
| **权益模板（Benefit Template）** | 商品与权益之间的绑定配置：一个商品可绑定多个权益项 |
| **监护人同意** | 处理未满 14 周岁儿童个人信息前，必须取得的父母或其他监护人的明示同意 |
| **request-id** | 一次 HTTP 请求全链路唯一标识，用于日志串联与问题定位 |
| **域（Domain）** | 按业务边界划分的代码与数据归属单元，本项目分为 D1–D9 共 9 个域 |
| **冻结域（D9）** | IM 与个人账本，停止新需求，仅保留可用性与配置开关 |

- BR-PERM-01：权限点采用 `资源:动作` 命名，权限检查统一在路由依赖层完成，不在 service 内散落。

### 5.1 M0-1 掌握度模型 v1

#### 5.1.1 背景与目标

**现状**：系统已有 `wrong_records`（错题本）、`study_errors`（学习错题）、`vocab_progress`（单词进度）三套分散的「掌握」记录，但都是**题目维度**而非**知识点维度**，且互不统一。家长看到的只有「做了多少题、错了多少题」，看不到「真正掌握了多少」。

**目标**：建立统一的「学生 × 知识点」掌握度矩阵，使：
1. 每个学生在每个知识点上有**可解释**的掌握度分值；
2. 掌握度能驱动个性化推荐、学情报告、诊断测评；
3. 掌握度提升量成为北极星指标。

#### 5.1.2 用户故事

| # | 角色 | 故事 | 价值 |
|---|---|---|---|
| US-1 | 学生 | 我想知道哪些知识点我已经掌握了、哪些还不会，这样我不用盲目刷题 | 学习效率 |
| US-2 | 家长 | 我想看到孩子在各知识点上的掌握情况，而不是只看到分数 | 效果可信 |
| US-3 | 教研 | 我想知道某知识点在全站的普遍掌握度，用于调整内容难度 | 内容优化 |
| US-4 | 运营 | 我想看到「掌握度提升」这个指标的变化，用于判断产品是否有效 | 战略衡量 |

#### 5.1.3 功能点

| 编号 | 功能点 | 优先级 | 说明 |
|---|---|:--:|---|
| FR-M0-1-01 | 知识点树管理 | P0 | 支持小学 1–6 年级 + 初中 7–9 年级三科（数学/语文/英语）知识点树的 CRUD、层级（学科→年级→单元→知识点）、依赖关系到配置 |
| FR-M0-1-02 | 题目-知识点标注 | P0 | 为 `questions` / `paper_questions` / `middle_questions` 打知识点标签，支持单题多知识点（主知识点 + 副知识点） |
| FR-M0-1-03 | 掌握度计算 | P0 | 基于答题记录计算每个「用户 × 知识点」的掌握度分值，支持全量重算与增量更新 |
| FR-M0-1-04 | 掌握度查询接口 | P0 | 按用户/知识点/学科/年级维度查询掌握度，支持热力图所需的二维数据 |
| FR-M0-1-05 | 掌握度后台查询 | P0 | 运营/教研可在后台按用户查询其掌握度矩阵与计算依据（可解释） |
| FR-M0-1-06 | 掌握度快照 | P1 | 每日/每周对活跃用户做掌握度快照，用于趋势曲线与提升量统计 |
| FR-M0-1-07 | 批量标注工具 | P1 | 教研批量导入题目-知识点映射（CSV/Excel），支持 AI 预标注 + 人工校正 |
| FR-M0-1-08 | 知识点覆盖率报表 | P1 | 统计「有知识点标签的题目占比」「有掌握度记录的知识点占比」 |

#### 5.1.4 业务规则

**掌握度算法（v1）**

```
mastery(user, kp) ∈ [0, 100]

输入信号（来自 attempt_answers / wrong_records / study_errors）：
  - 正确率   C = 近 N 次作答中正确的比例（默认 N = 10，覆盖最近 30 天）
  - 用时比   T = 该题平均用时 / 该知识点全站平均用时（T < 1 表示更快）
  - 时效性   R = exp(-Δt / λ)，Δt = 距最近一次作答天数，λ = 14 天（半衰期约 10 天）
  - 难度     D = 题目难度系数（1-5，归一化到 [0.6, 1.4]）
  - 连续正确 S = 当前连续正确次数（correct_streak）

计算公式：
  base      = 100 × C_adj × D_weight
  C_adj     = C × (0.7 + 0.3 × clamp(T_normalized, 0.5, 1.5))   # 做对且快 → 加分；做对但很慢 → 减分
  D_weight  = 0.6 + 0.4 × (D - 1) / 4                            # 难题做对权重更高
  streak_bonus = min(S, 5) × 2                                   # 连续正确最多加 10 分
  mastery   = clamp((base × R + 100 × (1 - R) × prior) + streak_bonus × R, 0, 100)
  prior     = 该知识点的先验掌握度基准（默认 20，表示「未学过」不是 0 分）

掌握度分档：
  0-30   未掌握（红）   → 优先安排学习与练习
  31-60  薄弱（橙）     → 需要巩固
  61-85  基本掌握（黄） → 定期复习
  86-100 已掌握（绿）   → 降低练习频率，进入长期复习队列
```

| 编号 | 规则 |
|---|---|
| BR-M0-1-01 | 掌握度计算为**幂等**：相同输入必得相同输出；支持按 user_id 全量重算 |
| BR-M0-1-02 | 未作答过的知识点**不产生记录**（避免全矩阵爆炸），查询时按 `prior=20` 兜底返回 |
| BR-M0-1-03 | 一道题可关联多个知识点，主知识点权重 1.0，副知识点权重 0.5 |
| BR-M0-1-04 | **题目必须挂载知识点**才能参与掌握度计算；未标注题目产生的答题记录计入「未归因答题量」指标，不进矩阵 |
| BR-M0-1-05 | 退化为「只错不练」的知识点：若 30 天无新作答，掌握度按 R 自然衰减，但不低于 prior |
| BR-M0-1-06 | 掌握度**只用于推荐与展示，不用于评价学生本人**；家长端展示必须附带「这是基于练习数据的估算」说明，避免误导 |
| BR-M0-1-07 | 算法参数（N、λ、权重）必须配置化，支持 A/B 实验与离线回测，禁止硬编码 |

### 5.2 M0-2 交易与会员体系 v1（人工支付网关）

> 🔴 **本节为 2026-09-02 评审定案内容，与 `01-产品优化方案.md` §3.3 一致。**

#### 5.2.1 背景与目标

**现状（实测）**
- 支付 / 订单 / 订阅端点数：**0**。
- 钻石充值：前端展示 `/api/diamond/recharge/config` 返回的静态二维码，用户转账后运营人工核对并手动加钻 —— **无订单、无状态机、无流水、不可对账**。
- VIP：`vip_users` 表仅 `(user_id, note, created_at)`，**无权益定义、无到期时间、无购买入口**，只能由管理员在后台 `/api/admin/vip` 手动开关。

**本期目标**
1. 建立完整的商品 → 订单 → 支付 → 权益 → 对账链路，但**支付环节采用人工核销**；
2. 让 VIP 从「管理员开关」变成「用户可自助购买、有明确权益、有到期时间」的正规商品；
3. 让钻石充值从「人工转账」变成「有订单可追溯、有状态机、可对账」的流程；
4. 通过支付网关抽象层，保证**未来接入第三方支付时业务代码零改动**。

#### 5.2.2 核心决策：人工支付网关

| 决策项 | 结论 |
|---|---|
| 是否接入第三方支付 | ❌ 本期不接入（微信支付 / 支付宝 / 银联均不做） |
| 用户如何支付 | 前端展示收款二维码 + 订单号 + 应付金额，用户线下扫码/转账 |
| 如何确认到账 | 运营在后台「待核销订单」中核实收款流水后，点击【确认收款】 |
| 确认后发生什么 | 订单置为已支付 → 权益发放引擎自动发放权益 → 订单置为已履约 → 通知用户 |
| 未来如何切换 | 实现 `PaymentGateway` 接口的新实现类，配置切换；**订单服务与权益发放代码不改** |

#### 5.2.5 业务流程

```
【用户端】
① 商品列表页  →  ② 商品详情页（价格+权益说明+退款政策+监护人同意勾选）
      ↓
③ 点击「立即购买」→ 创建订单（状态 PENDING_PAYMENT，24h 有效）
      ↓
④ 支付页展示：
   · 收款二维码（微信/支付宝收款码，配置化）
   · 订单号（大字）+ 应付金额
   · 付款备注格式要求：「订单号后 6 位」→ 如「备注请填写：AB12CD」
   · 倒计时 24:00:00
   · 客服联系方式
      ↓
⑤ 用户线下扫码转账，按格式填写备注

【运营端】
⑥ 运营在收款账户看到入账 → 进入后台「待核销订单」
      ↓
⑦ 用订单号后 6 位 / 金额 / 时间 搜索定位订单
      ↓
⑧ 打开核销表单：
   · 系统自动带出：订单号、商品、应付金额、下单用户、下单时间
   · 运营填写：实收金额、外部流水号（银行/支付工具流水号）、上传凭证截图、备注
      ↓
⑨ 点击【确认收款】→ 系统校验（见 BR-M0-2-05）
      ↓
   ├─ 校验失败 → 提示具体原因，不提交
   ├─ 金额 ≥ 阈值 → 进入待审批队列（状态 PENDING_APPROVAL）
   └─ 校验通过 → 状态置为 PAID
      ↓
【系统自动】
⑩ 权益发放引擎按权益模板发放（幂等，见 BR-M0-2-08）
      ↓
⑪ 订单置为 FULFILLED，写审计日志，触发埋点 order_paid
      ↓
⑫ 站内信/消息通知用户「会员已生效 / 钻石已到账」

【审批流（大额）】
PENDING_APPROVAL → 审批人复核凭证 → 通过(PAID→发放) / 驳回(回 PENDING_PAYMENT 并记原因)
```

#### 5.2.6 业务规则

| 编号 | 规则 |
|---|---|
| BR-M0-2-01 | **订单号规则**：`yyyyMMddHHmmss + 6 位随机大写字母数字`，全局唯一，用于人工核销定位 |
| BR-M0-2-02 | **幂等键**：创建订单时客户端传 `idempotency_key`（同一用户同一商品 5 分钟内重复提交返回同一订单），服务端 `(user_id, idempotency_key)` 唯一索引兜底 |
| BR-M0-2-03 | **权益快照**：订单创建时把商品的价格与权益模板**快照**进订单，后续商品改价不影响已创建订单 |
| BR-M0-2-04 | **金额单位**：统一用「分」（Integer），禁止 Float 存金额（现有 `diamond_accounts.balance` 为 Float，钻石可用浮点，但订单金额必须整型分） |
| BR-M0-2-05 | **核销校验清单**（任一不通过则拒绝）：① 订单处于 `PENDING_PAYMENT`；② 操作人具备 `order:confirm_payment`；③ 实收金额 ≥ 应付金额 × 0.99（允许 1% 手续费偏差，差额需备注）；④ 外部流水号在系统中不存在（`pay_transactions.external_no` 唯一索引）；⑤ 该操作人近 1 小时核销笔数 < 阈值（默认 50）；⑥ 凭证（截图 URL）必填 |
| BR-M0-2-06 | **大额审批**：实收金额 ≥ `ORDER_APPROVAL_THRESHOLD_FEN`（默认 50000 分 = 500 元）时，核销后订单进入 `PENDING_APPROVAL`，需**另一名**具备 `order:confirm_payment` 权限的人审批；审批人不能是核销人本人 |
| BR-M0-2-07 | **超时关单**：`PENDING_PAYMENT` 订单创建满 24 小时自动置为 `CLOSED`；关单前 1 小时给用户发一次提醒；已关单订单不可再核销（如需补单，走人工补单入口并记录原因） |
| BR-M0-2-08 | **权益发放幂等**：以 `(order_id, benefit_item_id)` 为幂等键，发放前先查 `benefit_grants` 表，已存在则跳过；发放与订单状态更新在同一事务内 |
| BR-M0-2-09 | **会员时长叠加**：已有未到期会员再购买 → 在 `vip_end_at` 基础上顺延；已到期 → 从当前时间起算；不可重复领取同一订单权益 |
| BR-M0-2-10 | **会员到期降级**：到期后进入 7 天宽限期（宽限期内保留权益并每日提醒续费），宽限期结束降级为免费用户；降级不删除数据，仅关闭权益 |
| BR-M0-2-11 | **钻石入账**：复用现有 `diamond_accounts` / `diamond_ledger`，`reason` 增加枚举值 `purchase`（购买）与 `refund`（退款扣回）；`ref_id` 存订单号，可对账 |
| BR-M0-2-12 | **退款扣回**：退款时优先扣回未消耗的钻石；若钻石已消耗导致余额不足，允许余额为负并**冻结账号的权益使用**，直至补正；会员按剩余天数比例折算退款金额 |
| BR-M0-2-13 | **冲正与退款分离**：冲正是「运营操作错误」的撤销（订单回到 `PENDING_PAYMENT`，可重新核销）；退款是「用户要回钱」（订单终态 `REFUNDED`，不可恢复） |
| BR-M0-2-14 | **外部流水号唯一**：同一 `external_no` 只能绑定一笔订单，防止一笔实际收款被重复核销到多个订单 |
| BR-M0-2-15 | **监护人同意**：下单前必须勾选「已阅读并同意《儿童个人信息处理规则》与《退款政策》」，记录 `guardian_consent_at` 与规则版本号；未同意不可下单 |
| BR-M0-2-16 | **未成年人退款**：未成年人消费退款申请，运营需在 48 小时内响应；退款政策在下单页与订单详情页显著位置展示 |
| BR-M0-2-17 | **收款码配置化**：收款二维码 URL 存 `system_config`（现有配置表），支持按渠道配置多个；不在代码中硬编码 |
| BR-M0-2-18 | **核销日报**：每日 01:00 自动生成前一日核销日报；未确认（无负责人签字）的日报在后台标红提醒 |
| BR-M0-2-19 | **不可删除**：订单、支付流水、权益发放记录、审计日志**一律不可物理删除**，只能状态变更 |
| BR-M0-2-20 | **支付网关抽象**：订单服务与权益发放服务**禁止** import 任何具体支付实现；只能依赖 `PaymentGateway` 接口 |

#### 5.2.7 状态机

**订单主状态机**
```
                      ┌──────────────── 24h 超时 ───────────────┐
                      ↓                                          │
  (创建) ──► PENDING_PAYMENT ──核销──► PAID ──发放成功──► FULFILLED (终态)
                      │                  │
                      │                  └─发放失败──► PAID (重试/人工介入)
                      │
                      ├─用户取消/超时──► CLOSED (终态)
                      │
                      └─核销(大额)──► PENDING_APPROVAL ──审批通过──► PAID
                                            │
                                            └──审批驳回──► PENDING_PAYMENT
```

**退款 / 冲正**
```
FULFILLED ──用户申请退款──► REFUNDING ──审批通过+扣回权益──► REFUNDED (终态)
                                │
                                └──审批驳回──► FULFILLED

PAID / FULFILLED ──运营发现核销错误──冲正──► REVERSED (终态)
                                              └─同时回收权益，原订单号不可复用
```

**会员状态机**
```
免费用户 ──购买生效──► VIP_ACTIVE ──到期──► VIP_GRACE(7天) ──宽限期结束──► 免费用户
                          ↑                      │
                          └────── 续费（重新下单）──┘
```
