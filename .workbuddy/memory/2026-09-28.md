### 架构决策

  前端 tab `gaoxiang`（桌面侧边栏「学习」组末位；移动 TabBar 6 项已满故不加）。

### 关键实现点
- 出题**题库优先**：先取该用户未做过的落库题，不足才 AI 补生成并落库 → 同内容不重复扣费。
- **服务端判分**（答案存库、不下发前端；多选须全对），错题闭环与小学同构（连对 3 次自动掌握）。
- 案例分析：AI 出大题（背景+子问题）→ 作答 → AI 按要点批改评分 0-100 落库。
- AI 调用一律在 DB 会话外；成功后短会话落库 + 按 token 扣钻（失败不阻断）。

### 🚨 两个真实踩坑（都已固化）
1. **`/quiz/generate` 必须用独立短会话回读**：AI 补题写库后若用请求级会话（Depends(get_db)）
   回读，REPEATABLE READ 快照冻结 → 读不到新行，表现为"AI 出题成功但返 0 题"。
   现改为：短会话1 查题库 → 会话外调 AI → 短会话2 回读。
2. **测试里会话 close 后不能再取 ORM 属性**（DetachedInstanceError）：`_seed_question` 改为
   在 commit 后立刻返回 `id`，用例用 id 而不是对象。
3. 测试断言设计坑：用 count=5 验证"题库优先不调 AI"是错的 —— 库存 1 道时 AI 仍会补 4 道
   （属预期）。验证不调 AI 必须让 **count == 库存数**。

### 🚨 纠正上一轮我写错的记忆（重要）
上一轮我记录「全量 pytest 加 `--basetemp=temp/pt` 减少系统 temp 删除拦截」——
**这条是错的，会造成大量假失败**：pytest 收尾 rmtree 该目录时会触发本机安全删除守护的
批量删除拦截 → 抛 `SystemExit` → fixture finalizer 未消费 →
后续用例在 setup 阶段连锁报错（`assert not self._finalizers`），
表现为 build_info/ops_check/preflight/requirements 一片红（25 例）。
**阈值是数量**：小批量跑（74 例）不触发 → 出现"小批量过、全量挂"的迷惑现象，
一度让我误判为"并发改文件竞态"。
**正确做法：用默认临时目录**（系统 temp 在守护的 bypass 名单里），
判通过看 `--junit-xml` 的 failures/errors 计数。
已同步写入 DEPLOY.md §12.1 与本文件下方 MEMORY.md。
