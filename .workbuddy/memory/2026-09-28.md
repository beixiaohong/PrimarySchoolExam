## 【午后追加】终于找到「零 Web 订阅」的根源：浏览器跟踪防护把 OneSignal 拦了（提交 272edc1）

用户反馈：**设置页「没有弹出授权提示」**，并在 Edge 里看到
「隐私、搜索和服务 → 跟踪防护 → 已阻止的跟踪器 → **OneSignal**」。
这一条直接把上午那个「`players=1` 且只有 `{'Email':1}`」的谜团串起来了。

### 事实链（都可复核）
1. **Edge 的跟踪防护用的是 disconnect.me 的开源 Tracker Protection 列表**（微软官方文档明写）。
   抓 `services.json` 实测：`分类 Advertising → 公司条目 OneSignal → 归属域名 onesignal.com`。
2. **Edge 官方分级处置表**（"Current tracking prevention behavior"）：
   `S` = 仅阻止存储访问；`B` = 阻止存储 **+ 阻止资源加载（网络请求被拦）**。
   | 级别 | Advertising | Analytics | Content | Social |
   |---|---|---|---|---|
   | 基本 | – | – | – | – |
   | **均衡（默认）** | **S** | – | S | S |
   | 严格 | **B** | B | S | B |
3. 我们的实现有 3 处依赖 `cdn.onesignal.com`：`OneSignalSDK.page.js`（590B loader）
   → `OneSignalSDK.page.es6.js`（141KB 真 SDK，**由 loader 自己再去取**）、
   以及 SW 内 `importScripts(.../OneSignalSDK.sw.js)`。站点服务器侧实测三者都 200
   （所以不是 CDN/网络问题），**是被用户浏览器拦掉的**。
4. 链路：脚本被拦 → `window.OneSignal` 永不出现 → **授权提示根本没机会弹**
   → 一个 Web 订阅都建不起来 → 后端一切推送必然 `no_subscription`。

**关键判据（以后别再绕）**：Edge **默认「均衡」只会让广告类「仅阻止存储」**，
脚本仍可加载、仍能订阅；**只有「严格」（或 Firefox 严格 / uBlock / AdGuard / 企业策略）
才会阻止资源加载**，才会出现「连提示都不弹」。所以出现本症状先查用户浏览器的防护级别。

### 🚫 排掉了一条看似合理的弯路：自托管 SDK 资源 **无效**
直觉做法是「把 `page.es6.js` / `sw.js` 下载到自己域名，SW 改 `importScripts('/本地文件')`」。

## 🔴 关键事实：国内环境下各浏览器推送端点的可达性（决定推送方案形态）

用户实测（线上阿里云服务器）：`curl https://fcm.googleapis.com/` → **exit=124 超时**；
沙箱实测（国内本地网络）：同域名 → **exit=56 连接重置**。进一步对照发现：

| 端点 | 归属浏览器 | 国内可达 | 实测证据 |
|---|---|---|---|
| `fcm.googleapis.com` | **Chrome / 国产 Chromium** | ❌ | 超时(124) / 重置(56)；DNS 解析正常(216.239.x.x)，是 **TCP 层阻断** |
| `*.notify.windows.com` | **Edge（Windows）** | ✅ | `sg2p` / `wns2-sg2p` / `par02p` 均返 **404**（=TLS+HTTP 往返成功）；裸域 56 |
| `updates.push.services.mozilla.com` | Firefox | ✅ | 406 |
| `web.push.apple.com` | Safari / iOS | ✅ | 405 |
| `push.opera.com` | Opera | ❌ | 56 |

- **`www.google.com` / `www.googleapis.com` 同样不可达** → 不是 FCM 被特判，是**服务器出网到
  Google 整体被阻断**。
- 🚨 **重大认知修正：Edge 的 Web Push 端点不是 FCM，而是微软自家的 WNS**（`*.notify.windows.com`）。
  Edge 有 `ForceBuiltInPushMessagingClient` 策略（用内置 WNS 客户端连 WNS），证实这条链路独立于 Google。
- 结论：**自建原生 Web Push 在国内服务器上「不需要出海通道/中转」**，只要受众是
  Edge / Firefox / Safari；真正无解的是 Chrome 与 Opera（端点硬编码 FCM/Opera Push，国内不通，
  且**浏览器侧连订阅都建不起来**——这也可能是 OneSignal 面板「零 Web 订阅」的另一半原因）。
- 推论：**Chrome 用户在国内的 Web Push 无论用谁家服务都不可用**（浏览器侧到不了 FCM）；

### 🚨 授权失败的真正根因：`www.liusijin.com` 与 `liusijin.com` 是两个源
用户实测打印 `页面: https://www.liusijin.com/#/settings`，而排查时给的白名单地址是
`https://liusijin.com`（不带 www）→ **改的权限落到了另一个源上**，当前页面读回仍是 `default`。
- 浏览器把 `www.liusijin.com` 与 `liusijin.com` 视为**两个独立 origin**：通知权限、
  Service Worker、**推送订阅**全部互不相通。表现为「设置里明明改成允许了，页面却还是 default」。
- 排查此类问题的**第一步应当是先打印 `location.href` / `location.origin`**，不要凭域名想象。
- ⚠️ 隐患：两个源各自会产生**一套独立订阅**，同一用户可能收到**两份推送**。
  OneSignal 后台配的 `chrome_web_origin` 是 `https://liusijin.com`，而用户实际在用 `www` 访问。
  → 建议**统一域名**（nginx 301 把 www 跳转到非 www，或在 OneSignal 后台补上 www 的 origin）。
- 另：`copy()` 不是所有控制台环境都有（用户处报 `copy is not defined`），
  测试脚本改用 `alert()` 输出更稳妥。
