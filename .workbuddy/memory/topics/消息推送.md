- **第三条通知通道**（与 `send_email`/`send_sms` 同构：`*_configured()` + 尽力而为的 `send_*()`），属 **D8 platform 域**：`services/push.py`、用户端 `routers/push.py`（`/api/push/*`）、后台 `routers/admin_push.py`（`/api/admin/push/*`）。跨域经 `platform.contracts`（新增边 frozen→platform，须复验 `lint-imports = 2 kept, 0 broken`）。
- 表 3 张（迁移 `083_push_onesignal.py`，幂等三步）：`push_subscriptions`（`subscription_id` 唯一 upsert；换账号改写归属并复活 `revoked_at=None`）、`push_prefs`（`user_id` 唯一）、`push_logs`（`dedup_key VARCHAR(120) NULL` 唯一 + `user_id`/`event` 时间索引）。
- **OneSignal v16 API 要点**：`POST https://api.onesignal.com/notifications`，Header `Authorization: Key <REST_API_KEY>`（**不是 Bearer**）；定向用 `include_aliases.external_id`（= 本系统 `user_id`）+ `target_channel:"push"`；广播用 `included_segments:[push.SEGMENT_ALL_SUBSCRIBERS]`（**不要写字面量**，见下条）。
- 🚨 **HTTP 200 但响应无 `id` 表示靶向受众无有效订阅** → **必须判为失败**（`ok=False` + `err="no_subscription"`），否则是「假成功」；**失败不写 `dedup_key`**，保证可补发。
  **该判定必须两条发送路径共用**：`_send_once`（定向）与 `send_to_all`（段推送）曾各自实现，段推送漏判 → 线上表现为后台「结果=失败、错误=空」而接口同时回「已广播」（两头矛盾、无从排查）。已抽 `_parse_resp()` 共用。
- 🚨🚨 **同一个 `no_subscription` 有「两种」风马牛不相及的原因**（2026-09-28 一天内各踩一次，务必都会排查）：
  1. **真没人订阅** —— 订阅构成里没有 Web 订阅；
  2. **群发分段名过期** —— 代码里写死的段名在 OneSignal 侧已不存在。**引用不存在的段时接口同样返回 200 却不带 `id`**，现象与第 1 种完全一样，而文案提示「还没人授权通知」→ 排查方向被彻底带偏。
  · OneSignal 已把预置段从「用户」维度改成「订阅」维度：旧名 `Subscribed Users` **已不存在**，实测 App 内只有 6 个段——`Total Subscriptions`、`Active Subscriptions`、`Inactive Subscriptions`、`Engaged Subscriptions`、`All SMS Subscriptions`、`All Email Subscriptions`。
  · 段名已抽常量 `push.SEGMENT_ALL_SUBSCRIBERS`（常量处写了核对手册），并由 `test_broadcast_segment_name_is_pinned` 钉住；`no_subscription` 的返回文案已改为**并列提示两种原因**。
  · **判据：群发 0 人、但定向推送成功 → 是段名问题，不是订阅问题。** 只读核对：
    `GET https://api.onesignal.com/apps/{app_id}/segments` 列段名 → `GET .../segments/{segment_id}` 得 `{"subscriber_count": N}`。
  · 实测值（2026-09-28）：`Total Subscriptions`=3、`Active Subscriptions`=2；换新段名群发 → **200 + 有 id、`successful=1`**（旧段名那条 `1f0fc31e` 是 `successful=0`）。
- 🚨 **Email / 移动端订阅不能用于 Web Push**（段推送同样发不到，也是 200 无 `id`）。判订阅类型看 `GET api/v1/players` 的 `identifier` 形态：`http(s)://` 开头 = Web 订阅，含 `@` = Email（比 `device_type` 可靠；实测 Web = `device_type=5`）。注意**段人数 ≠ 能收到 push 的人数**——`Total Subscriptions`=3 里有 2 个是 Email。
  **排查「推送发不出去」第一步先跑只读工具 `tools/onesignal_probe.py`**（已含 **[3] 分段名核对**节），它能区分三种方向相反的原因：配置错 / 没人订阅 / 段名过期。
- 🚨 **浏览器跟踪防护会把 OneSignal 拦掉**（2026-09-28 定位，见文档 §13）：`onesignal.com` 在 disconnect.me 跟踪防护列表里属 **Advertising** 类。
  · Edge **均衡（默认）**只阻止存储 → 脚本仍能加载、仍可订阅；Edge **严格**、Firefox 严格、uBlock Origin/AdGuard、企业策略 → **阻止资源加载** → `window.OneSignal` 永不出现 → **连授权提示都不弹**（不是用户拒绝，是没机会问）→ 后端所有推送必然 `no_subscription`。
  · **自托管 SDK 资源解决不了**：SDK 运行期仍必须请求 `api.onesignal.com`（同属该实体 → 照样被拦）；且 v16 的 `OneSignalSDK.page.js` 只是 590B loader，内部**硬编码** CDN 的 `page.es6.js?v=160610` 地址，连 loader 也没法自托管。**别走这条路。**
  · ⚠️ **旧结论「彻底规避只有改用第一方 SW + 原生 VAPID Web Push」已被实测推翻，别再照做**：线上服务器到 `fcm.googleapis.com` 被网络阻断（Google 系整体不可达），而**投递是由服务器发起的**——所以 **Chrome/Opera 用户的 Web Push 永久发不出去**，自建方案只覆盖 Edge(WNS)/Firefox/Safari。**OneSignal 的投递在自家海外服务器上，恰好绕过该限制，覆盖面反而最大**（实测自建 Edge 路线本身是通的：pywebpush → WNS → `HTTP 201 X-WNS-STATUS: received`）。完整事实链、五端点可达性表与两个必踩的坑（`x-wns-cache-policy`、同源单订阅冲突）见 `docs/推送通知(OneSignal)接入说明.md` **§14**。
- **Service Worker 必须在域名根路径**（scope = 所在目录）；本项目 nginx 全量反代 + `web/dist` 不作静态目录暴露 → 由后端专用路由 `GET /OneSignalSDKWorker.js` 提供（优先 `WEB_DIST_DIR/OneSignalSDKWorker.js`，缺则 `ONESIGNAL_WORKER_FALLBACK` 内联兜底；headers 带 `application/javascript` + `Service-Worker-Allowed: /` + **`Cache-Control: no-store`**，后者是 OneSignal 硬要求）。**路由需同时接受 GET 与 HEAD**（`@app.get` 不补 HEAD → `curl -I` 405 会误判成部署失败）。
- **密钥只走后台「系统配置 → 消息推送」在线填写**（`sysconfig` 优先级：`system_config` 表 > `.env` > 默认值，60s 缓存）；`push_sdk_config()` **不下发 REST_API_KEY**；后台 status 接口**不回传密钥片段**。
  · 实况：本地 `.env` **已含真实凭据**（App ID 36 位 UUID，REST Key `os_v2_app_…`），因此**本地 `http://127.0.0.1:8000` 即可端到端真机测试**（`push.js` 对 localhost 传了 `allowLocalhostAsSecureOrigin`，绕开 HTTPS 限制）；本地库 `schoolexam` 已应用迁移 083（3 张 push 表）。⚠️ 本地测试写的 `push_*` 都落在**克隆库**，与线上无关，别据此判线上订阅数。
- **防打扰四道闸**：设备开关 → 场景偏好（study/im/announce/exam 四类）→ 免打扰时段（`quiet_start/quiet_end`，跨零点反向判断；**不复用** `check_quiet_hours`）→ 每人每日上限 `DAILY_CAP=8`（公告/群发 `_UNLIMITED_EVENTS` 不占额度）。
- **IM 离线推送**在 `frozen/routers/im.py`：`asyncio.create_task(asyncio.to_thread(_push_offline_members, ...))`（避免阻塞事件循环、不持 DB 连接），只推非在线成员，`key_template="im:{uid}:{chat_id}:{date}"`（每人每群每日一条）。

- 前端 `logic/push.js`：SDK **懒加载**（config.enabled 才注入，通道未配时零第三方请求）、**登录后才 `login()`**（游客不登录，否则订阅绑到空/错的 external_id）、失败全静默但**必须可见**（`pushSdkError` + `_pushLoadSdk` 的 10 秒超时兜底——脚本被拦时 `onerror` **不保证触发**，没超时就会永远停在「未开启」，用户和我们什么都看不出来）。
